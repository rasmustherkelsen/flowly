# Message Stream Verification Records

Observations from runs against live brokers and the Azure Event Hubs emulator that back the design decisions in `.claude/rules/message-streaming-conventions.md`. The rules file keeps the resulting behaviour as rules; this file keeps the evidence (versions, figures, scenarios, and what was not verified). It is not loaded automatically: read it when changing the behaviour a section covers, and re-verify against the versions named in it before relying on a figure.

## RabbitMQ start offset probe

- **Verified against a live broker** (RabbitMQ 4.3.1, `rabbitmq:4.3-management` with `rabbitmq_stream`, `RabbitMQ.Client` 7.2.2, `RabbitMQ.Stream.Client` 1.12.0; AMQP port and Stream port published on loopback): `last` probe returned the exact next offset on streams of 0, 1, 7, 100, 5 000 and 50 000 messages, on a size-truncated stream, on each partition of a 3-partition Super Stream, and on a 20 000-message uncompressed sub-batch chunk (with batched acknowledgements; with per-message acknowledgements and a 300 ms cap it stopped at 8 762, which is why collection is not cut off earlier). First delivery came 0 to 15 ms after the consumer attached, also on a stream being written to by four publishers while six consumers read it, so 1 s is a wide margin for "nothing arrives". Offsets are not dense: stream offset tracking written by a Stream protocol consumer and the snapshot at every new segment occupy offsets (2 000 messages ended at offset 2 013), and the probe reported the last message offset plus one, which can only be lower than the real next offset. A numeric `x-stream-offset` below the retention floor is clamped to the first retained message; one beyond the tail attaches without an error and waits. Timestamps are in whole seconds and the first delivered message was the first at or after the time in every case tried (chunk-granular lower bound is the documented behaviour, no straddling chunk was observed). Probes called from inside `ConsumerUpdateListener` for 12 partitions ran concurrently, took about 210 ms each when the partitions held messages and about 5 s with a 5 s attach timeout when empty, and left no consumer and no channel behind. A listener callback blocked for 70 s made the broker close the stream connection after 60 s and the client fired the listener again, confirming the documented 60 second limit, so the probe (about 1 s on an empty partition) fits well inside it. Compressed (gzip) sub-batches written by a Stream protocol producer delivered nothing to an AMQP consumer at all, so such a stream reads as empty to the probe, as it already does to the handler's own AMQP consumer.
- **End to end against the live broker:** empty non-partitioned stream plus `Last` plus a SQLite checkpoint, stop, publish 5, restart: all 5 delivered (stored position after the first run `-1`; the same sequence on the previous code stored an empty position and delivered nothing). Same on a 3-partition stream with 30 messages: all 30 delivered. A stream already holding 10 messages seeds `9`, and only the 3 messages published afterwards were delivered. `Timestamp` on an empty stream seeds `-1`; with messages that are all older than the time the seed is not stored (warning, lazy bootstrap); with messages on both sides of the time the first delivered message was the first one at or after it. A first start costs about 0.3 s more with messages in the stream and about 1 s more on an empty stream or partition; later starts are unaffected.
- **Not verified:** clusters with more than one node, TLS, RabbitMQ 3.x and other 4.x versions, other client versions, a probe stalled by a loaded broker for longer than the attach timeout on a stream that is not empty (the passive count guards this only when it is non-zero), streams with more than a few hundred partitions started at once, and the effect of a very large last chunk on a slow link.

## RabbitMQ Super Streams

- **Behaviour verified against a live broker.** Verified against RabbitMQ 4.3.2 (the `rabbitmq:4-management` image with the `rabbitmq_stream` plugin) and `RabbitMQ.Stream.Client` 1.12.0, with several OS processes of one partitioned handler sharing a built-in SQLite checkpoint store, on a 12-partition and a 3-partition stream:
  - **Ownership.** `ConsumerUpdateListener` fires with `isActive: true` for every partition when a single instance runs. When a second instance joins, the broker sends `isActive: false` to the first instance for exactly the partitions that move and `isActive: true` to the joiner; the broker reports one `single_active` and one `waiting` consumer per partition stream. A gracefully stopped instance sends nothing for its own partitions — the survivor receives `isActive: true` — and a killed instance's partitions move to the survivor immediately. Restarting the instance moves a share back.
  - **`isActive: false`.** The callback fires reliably, and the offset returned for it is ignored: returning an arbitrary offset for every revoked partition changed nothing for either instance, and the later `isActive: true` call returned the resolved start position, which was honoured. The consumer returns `OffsetTypeFirst` for it.
  - **No revoke after a lost connection.** When the broker restarts, the client recovers each subscription and reports `isActive: true` again without a preceding `isActive: false`, so a partition can be assigned while this process still holds a processing loop for it. `RabbitMqPartitionedStreamConsumer.OnConsumerUpdate` revokes the live loop first and waits for every earlier revocation of that partition before it starts a new loop.
  - **Start position resolution failure.** When `resolveStartPosition` throws inside `ConsumerUpdateListener` (a checkpoint store outage was simulated for one partition of a 3-partition stream), the client does not propagate the exception and logs nothing; it subscribes that partition at its own default offset, `next`, ignoring the configured or stored start position, and the other partitions are unaffected. `RabbitMqPartitionedStreamConsumer.OnConsumerUpdate` therefore resolves the start position first, before registering the partition's processor and raising `PartitionAssigned`, and logs and rethrows a failure. No processing loop exists for that partition afterwards, no checkpoint is saved for it, and the messages the client still delivers for it are dropped and counted (see "Recovery of an unresolved start position" below, which also covers how the partition is retried). Resolving after the loop had started made the loop consume from the client's default offset, so a stored position was ignored without any log entry and later saves would move the checkpoint past the unprocessed backlog.
  - **Checkpoint resume.** After a restart each partition resumes at its stored position plus one (`StartPosition.Offset(saved + 1)`); nothing is replayed when nothing new was published. Graceful stop, `kill -9` and a broker restart lost no message. When a batch was in flight (handler effect visible, checkpoint not yet saved) at a `kill -9`, or at a rebalance, the new owner replayed exactly that batch: duplicates are bounded by one batch per affected partition.
  - **Partition index.** `{queueName}-{partition}` parsed from the source stream name matched the broker for every partition of a 12-partition stream, including 10 and 11: per-partition handled counts equalled the per-stream message counts on the broker.
  - **Start position.** Without a checkpoint, `First` replays every partition, `Offset(n)` applies `n` to each partition's own offset numbering, and `Timestamp(t)` delivers the messages published at or after `t` (the broker resolves timestamps at chunk granularity). `Last` is mapped to the stream protocol's `next` offset (`OffsetTypeNext`), so messages already in any partition are not delivered. The AMQP `last` and the stream protocol's `last` attach at the last chunk and would deliver the messages in it, so they must not be used for `Last`. With a checkpoint, `StartPosition` is a bootstrap value: `Last` and `Timestamp` are resolved to an offset and stored on the first run of that `(ConsumerName, Partition)` (see "First-run seeding" below), after which the stored position wins regardless of the configured value, and messages published while the process was down are delivered, including after a restart before any batch was processed (for example `Last` on an empty stream). Only when the seed cannot be resolved or stored is `StartPosition` re-evaluated until the first batch has been saved.
  - **Topology.** With `createTopology: true` the direct exchange, the `{queue}-{n}` streams (`x-queue-type: stream`, retention arguments applied) and the bindings with the partition index as routing key are created as described above. A Super Stream created with `rabbitmq-streams add_super_stream` (or by any other tool outside Flowly) is consumed and published to by Flowly unchanged when the host runs with `createTopology: false`; Flowly's own declaration is deliberately not made compatible with such a Super Stream, so `createTopology: true` against it fails on the AMQP declaration (see the "Partition drift" bullet below) and `createTopology: false` is the supported way to use it. With `createTopology: false`, `RabbitMqPartitionedStreamTopologyValidator` fails host startup both when the Super Stream is missing and when the broker's partition count differs from the one the contract declares; with `createTopology: true` the same count comparison runs after the additive declaration (see "Declared partition count is validated" above and the "Partition drift" bullet below).
  - **Partition drift (live broker, RabbitMQ 4.3.2, `rabbitmq:4-management` image, digest `sha256:76412b1ed2865b88ed01b4a504f72e888842f2089a7527743d325ce7c9d3a43b`, `rabbitmq_stream` plugin, `RabbitMQ.Stream.Client` 1.12.0; AMQP and Stream ports published on loopback, matching `streamPort` passed to `UseRabbitMq`).** All results are from a sender-side host (`AddMessageRecorder<T>()` on a partitioned contract), single node, started and stopped per run:
    - Exact match: a fresh broker with `createTopology: true` and `[StreamPartitions(3)]` created the exchange, three streams and three bindings and started; repeating with `createTopology: true` and with `createTopology: false` started.
    - Fewer on the broker than declared: a Super Stream with 2 partitions and `[StreamPartitions(4)]` with `createTopology: true` created the two missing streams and bindings and started (broker then reported four bindings with routing keys `0` to `3`); the same contract with `createTopology: false` then started. The `partitions` query returned the new count immediately after the AMQP declaration: 12 of 12 repeated runs that deleted the Super Stream and recreated four partitions from nothing started.
    - More on the broker than declared: a Super Stream with 4 partitions and `[StreamPartitions(2)]` and, separately, `[StreamPartitions(3)]` failed host startup with the message naming the stream, `4 partition stream(s)` and the declared count, with `createTopology: true` and with `createTopology: false`. After those failures the broker still had all four streams and four bindings (nothing deleted, nothing created).
    - A Super Stream created with `rabbitmq-streams add_super_stream <name> --partitions 3` started with `createTopology: false` and `[StreamPartitions(3)]`, and failed startup with the count message for `[StreamPartitions(2)]` and `[StreamPartitions(4)]`. With `createTopology: true` the AMQP declaration of such a Super Stream is rejected with `PRECONDITION_FAILED - inequivalent arg 'x-queue-leader-locator'` (also with `--leader-locator client-local`), before any count check: the declaration does not set that argument. This predates the count check. Flowly's declaration is deliberately not made compatible with Super Streams created outside Flowly: use `createTopology: false` for them.
    - A wrong `streamPort` with `createTopology: true` and a partitioned contract failed startup with `StreamSystemInitialisationException` ("no endpoints could be reached") in a sender-only host.
  - **Stream port.** A wrong `streamPort` fails host startup with `StreamSystemInitialisationException` ("no endpoints could be reached"). The configured endpoint is used for the initial connection and for stream metadata only; the connection that consumes goes to the `stream.advertised_host`/`stream.advertised_port` the broker reports for the partition's leader, except when the configured host is loopback, where the client keeps the configured endpoint. Against a non-loopback host, a broker that advertises an address the client cannot reach (for example the in-container port behind a published port mapping) fails host startup with "None of the brokers could be reached"; with the advertised host and port set to the reachable values the consumer connects. Flowly passes a single endpoint and no address resolver, so a load balancer in front of the stream port is not supported.
  - **Broker restart.** Restarting the broker while two instances consume: the client recovers all subscriptions on its own, consumption resumes, and messages published afterwards are delivered without loss or duplication.

## RabbitMQ halted partition held with backpressure

- **Halted partition held with backpressure (live observations).** Verified against RabbitMQ 4.3.1 (Erlang 27.3.4.12; the `rabbitmq:4.3-management` image, repo digest `sha256:93367c6be6e1f25f830a7750170cc27bca119873b6bbcafafa4a0d9cd616b7cb`, `rabbitmq_stream` and `rabbitmq_stream_management` enabled, one container with the AMQP, stream and management ports published to loopback, `stream.advertised_host = 127.0.0.1` and `stream.advertised_port` set to the published port), `RabbitMQ.Stream.Client` 1.12.0, `RabbitMQ.Client` 7.2.2, .NET 10, with a real Flowly host (handler `[BatchProcessing(5, 1)]`, `[RetryPolicy(1, 0)]`, a file checkpoint shared between processes) publishing sequence numbers at 30 to 100 messages per second and a fault injected for the batch holding chosen sequence numbers:
  - **Hold.** A 3-partition stream at 100 messages per second: the partition with the failing batch went `Halted` while the other two kept running with lag 0. The broker showed the halted partition's consumer position frozen at the failed batch's offset (1936), credits down from 2 to 1 and the lag growing by about 43 messages per second, to 9 784 after 3 minutes 40 seconds; the connection stayed open. The host logged no "not currently processing" warning (0 of them) and one retry warning; the only critical entry was the halt. After a forced garbage collection the managed heap was 1 to 2 MB throughout (the heap without a collection grew to 30 to 44 MB of garbage in the longer runs, which is why the memory figures here are taken after a forced collection), and the process working set went from 101 MB right after the halt to 105 MB 3 minutes 40 seconds later (91 to 97 MB before it).
  - **Resume in place.** Calling the internal resume hook for the halted partition returned `Resumed` (a second call `NotHalted`, a partition the process does not own `NotOwned`), the held batch (5 messages, attempted twice and failing before) was handled successfully once and the partition caught up with the backlog. Of 29 510 published messages every one was handled exactly once: no gap, no duplicate, strictly increasing within each partition.
  - **Non-partitioned stream.** An AMQP stream consumer at 60 messages per second: handled count frozen at the failed batch for 2 minutes while the publisher continued, no drop warning, working set 94 to 96 MB, managed heap 1 MB after a collection; after the resume (no partition argument) all 8 736 published messages were handled exactly once with the failed batch run twice before and once after.
  - **Revoke of a held partition.** One instance holding all three partitions (one failed batch each), a second instance started with the same consumer name and checkpoint store: partition 1 moved to the second instance within seconds, the first instance dropped its entry for it (the other two stayed `Halted`), the second instance replayed the failed batch first from the stored position and handled it successfully, and neither instance logged a "not currently processing" warning. Resume on the first instance for the moved partition returned `NotOwned`; resuming its other two worked. Of 2 562 published messages every one was handled exactly once.
  - **Stop while held and restart.** `SIGTERM` to a host holding all three partitions ended it in under a second without error entries; the delivery that was already in flight at the time produced 85 "not currently processing" warnings within about 15 ms (the chunks the client had already read for the partitions whose runners were cancelled, as at any stop). Nothing was checkpointed for the held batches; the restarted host handled exactly the three failed batches first and then the rest, 792 of 792 messages handled once.
  - **Test setup note.** Against a container the stream client connects to the advertised address; with `localhost` as the AMQP host and the stream port published on IPv4 only, the consumer's connection was refused (`None of the brokers could be reached`), so the host used `127.0.0.1` together with the matching `stream.advertised_host` and `stream.advertised_port`.
  - **Not verified here:** clusters with more than one node, a held partition on a stream with a `ConsumersPerConnection` above 1, a hold longer than 4 minutes, and a stream written by a publisher with several channels (a few sequence numbers arrived slightly out of publish order in the plain stream, also before any halt, which does not concern the consumer).

Not verified: the client's documented statements that the listener runs on the connection's socket thread and that the broker closes the connection when the callback takes longer than 60 seconds (the wait for a pending revocation of the same partition happens inside that callback), clusters with more than one node (leader moves, replica reads), TLS on the stream port, RabbitMQ 3.x and other 4.x versions, other `RabbitMQ.Stream.Client` versions, more than 12 partitions, and instances that stay unreachable for longer than the client's reconnect attempts.

## RabbitMQ recovery of an unresolved start position

- **Live observations** (RabbitMQ 4.3.1, image `rabbitmq:4.3-management`, digest `sha256:93367c6be6e1f25f830a7750170cc27bca119873b6bbcafafa4a0d9cd616b7cb`, `rabbitmq_stream` enabled, single node, ports published to loopback with `stream.advertised_host` and `stream.advertised_port` set to the published address; `RabbitMQ.Stream.Client` 1.12.0; a 3-partition stream, a hand-rolled file checkpoint whose reads fail on a switch file, batches of 5 messages, 20 messages per second per partition; the harness is not part of the repository):
  - **Short outage at assignment.** Store reads for one partition failing for about 15 s from host start: the resolution was retried at 0.5, 1, 2, 4, 5 and 5 s, the partition started 2.5 s after the store returned (17.5 s after it was assigned), the other two partitions ran from the start, and no message was dropped (no drop counter, no summary): 1088 of 1088 messages handled per partition, no duplicates. That run predates the change that records `waiting` only when the window ends: it recorded `waiting` from the first failed attempt (17.5 s of `waiting`, two transitions), and the other scenarios below were run in that form too, so their `waiting` intervals started at the assignment rather than at the window end; the short outage was re-run afterwards (see the next entry).
  - **Short outage, re-run after waiting began to be recorded at the window end.** The same short outage again (store reads for one partition failing for about 15 s from host start, the other settings unchanged): the resolution was retried inside the window (attempts at 0.5, 1, 2, 4, 5 and 5 s), the metrics sampled twice a second showed no entry for the partition and no `waiting` transition at any moment, `running` from the moment its loop started (about 18 s after the assignment, 3 s after the store returned), the other partitions ran from the start, no message was dropped, and 990 of 990 messages per partition were handled with no duplicates. Only this scenario was re-run; the outage-longer-than-window, two-instance and shutdown observations below were not.
  - **Outage longer than the window.** One partition's reads failed for 90 s from host start (a stored position existed from an earlier run). The window ended 40.0 s after the assignment, the partition was reported `waiting`, and the drop counter and summaries started (a first summary of 1 message at once, then about 100 and 200 messages summarized after each following window). The consumer was recreated 5.0 s after the first window ended and 10.0 s after the second (an earlier run with the store back after 140 s also saw the third, after 20.0 s). Closing, stopping the two live loops and creating the consumer took 35 to 67 ms. The two healthy partitions kept handling: in the 99 s around the two recreations the longest gap between two handled messages of a healthy partition was 0.39 s (the handler cycle was 0.37 s). With a handler that wrote its effect and then waited 370 ms honouring cancellation, each recreation redelivered exactly one batch (5 messages, the configured batch size) per healthy partition; with a 200 ms handler the recreations happened to fall between batches and redelivered nothing. After the store returned the partition started at the next recreation, 5.7 s later, from its stored position plus one: 2574 of 2574 messages per partition handled, none missing; the only duplicates were the redelivered batches and the batch of the host restart that preceded the outage.
  - **Two instances.** Instance A could not read the store for one partition, instance B could. B joining during A's window (the first window, or the second after one recreation): the broker activated the partition for B 21 ms after A's callback returned, A's `waiting` entry was cleared by the revocation, no recreation followed, and all partitions were handled without loss or duplication (the other two by A, the failing one by B). With A unable to read the store for any partition and B healthy, the broker kept activating a partition for A after each recreation of A: all three partitions stood still for A's first 40 s window, B then served two of them for good, and the third alternated: on B only between the end of A's window and A's next recreation (5, 10, 20, 40, 80 s later, then the 120 s ceiling), on A (active but unable to resolve, dropping) for 40 s after each. B restarted that partition's loop at each hand-back (one redelivered batch observed), and it progressed by 125 of 2970 messages in the six minutes before the run was stopped. Nothing was lost: the partition catches up from its stored position once a store works for the instance that holds it.
  - **Halted partition and a recreation (interplay).** Partition 0 halted by a failing handler (one retry, then held) 15 s after the host start while partition 1 could not read the store from the start: partition 0 was `halted` and partition 1 `waiting` side by side. At the first recreation (45 s) the state of partition 0 went from `halted` to removed and, after the consumer was created again, to `running` and `halted` again within 66 ms, as the replayed poison batch failed its retry (two `halted` transitions in total), with no "not currently processing" warning. After the failure switch was turned off the next recreation replayed the batch successfully and the partition continued. Partition 0 handled 3958 of 3958 messages with only one batch (5 messages) redelivered, at a recreation that found a batch in flight, and the healthy partition 2 redelivered one batch per recreation; nothing was skipped. Partition 1 resumed at the third recreation, after the store returned (it was still catching up when the run was stopped, 3940 of 3958 handled, contiguous). The closing of the consumer did not wait for the held delivery.
  - **Shutdown while waiting.** SIGTERM during the first window, 1.6 s after a recreation (settle time and window of the recreated consumer) and 9.5 s after one: each host exited with code 0 within about 0.1 s, logged no error and recreated nothing afterwards. A shutdown during the 35 to 67 ms of a recreation itself is covered by a unit test only.
  - **Stand-down after 3 failed recreations (live observations)** (RabbitMQ 4.4.0 on Erlang 29.1.2, image `rabbitmq:4-management`, digest `sha256:af6f50d38098d8bd52fef7f3fa85015dd8b2bf6def58e995bf584ae9ba0f6407`, `rabbitmq_stream` enabled, `stream.advertised_host` and `stream.advertised_port` set to the published loopback address; `RabbitMQ.Stream.Client` 1.12.0; a 3-partition stream, a hand-rolled file checkpoint whose reads fail while a per-instance switch file exists, batches of 5 messages, one publisher at 60 messages per second round robin (20 per partition per second), a handler that writes each handled message to a per-partition file; the harness is not part of the repository, and an earlier set of runs whose handler appended all partitions to one shared file lost lines and was discarded):
    - **Two instances, A unable to read the store, B healthy.** A started first and held all three partitions, B joined 8 s later; each run lasted 480 s and published about 29 970 messages, about 9 990 per partition. With the code before the stand-down existed, B handled partitions 0 and 2 completely (9 990 each) and partition 1, the one that stayed with A, 1 415 of 9 990 (14 percent), and A completed 5 recreations and never stood down. With the stand-down, B again handled partitions 0 and 2 completely and partition 1 5 430 of 9 990 (54 percent), A stood down once (60 s cool-down, logged after three recreations that had left the partition waiting) and completed 6 recreations (the one after the cool-down is the extra one), and B drained about 2 900 messages of the partition in one burst while A's consumer was closed. No handler error in either instance. Nothing was lost: the messages A dropped for the partition are the ones B handled from the stored position.
    - **The broker gives the partition back on rejoin.** When A created its consumer again after the cool-down, the broker made partition 1, and only partition 1, active on A again while partitions 0 and 2 stayed with B (the broker spreads the partitions of a super stream over the consumers of a group when one joins). A then waited, dropped and recreated again, and the partition lag grew until the next stand-down: the stand-down relieves the starvation for the length of the cool-down, it does not end it, and only one stand-down happened in the 8 minutes because the next one needs three further failed recreations (delays 40, 80 and 120 s).
    - **Lone instance.** One instance whose store reads failed from the start (switch removed about 230 s after the instance started, during the first cool-down): recreations after 5, 10 and 20 s, then the stand-down (60 s cool-down) once the third recreation still left the partitions waiting, consumer created again at the end of the cool-down, all three partitions started 0.6 s later (26 s after the store had returned, which is the remainder of the cool-down) and all 25 875 published messages were handled: 8 625 per partition, contiguous per partition, no duplicates, the 400 messages dropped per partition before that being the ones replayed from offset 0. The lone instance consumed nothing, healthy partitions included, for the length of the cool-down.
    - **Shutdown during a cool-down.** SIGTERM 5 s after the stand-down was logged: the process exited 0.06 s later, no further recreation or error was logged and the log's last entry stayed the stand-down.
    - **Counter and log.** The `flowly.message.stream.partition.stand_downs` counter and the warning are covered by unit tests; the live runs checked the log entry (cool-down 60 s, stand-down 1, 3 failed recreations) only. The counter was not read from a live exporter. Wall-clock time in the live runs was not reliable (the clock of the machine jumped during the runs), so only counts and ordering are reported, not timelines.
  - **Not verified:** clusters with more than one node, TLS, other RabbitMQ and client versions, more than three partitions or two instances, the second and later cool-downs live (1 to 5 minutes; their lengths and the ceiling are covered by unit tests), a stand-down with a halted partition on the same instance, a resolver that ignores cancellation, a store that hangs instead of failing, and a store outage that also fails the checkpoint saves of the healthy partitions (they halt, which is independent of this recovery).

## Azure Event Hubs emulator

- **Behaviour verified against the Event Hubs emulator.** Run with `Azure.Messaging.EventHubs` and `.Processor` 5.12.2, `Azure.Storage.Blobs` 12.23.0, the `mcr.microsoft.com/azure-messaging/eventhubs-emulator:latest` image (arm64, built 2026-06-30, digest `sha256:be413f0d59541621879e6d197d73f64f3b3ac5fa45861641fdc1430252b8b44b`) and `mcr.microsoft.com/azure-storage/azurite:latest` (built 2026-08-25), with the opt-in tests above and the `samples/AzureEventHubs/MessageStreamWithCheckpoint` sample. Every statement below is an emulator observation unless it names another source:
  - **Producing.** Events recorded with the same partition key (also from two separate senders) landed in one partition in send order; eight keyless records on a four-partition hub spread two per partition; the key is ignored on a non-partitioned contract; message id, correlation id, retry count, `traceparent`/`tracestate` and the body round-trip; `MessageProperties.StreamOffset` is the sequence number and is consecutive within a partition; a body above the batch limit throws `MessageTooLargeException` (the emulator's 1 MB event limit).
  - **Start positions.** `First` replays from the first retained event; `Last` delivers only events enqueued after the reader attached; `Offset(n)` delivers the event with sequence number `n` first; `Offset(stored + 1)` resumes after the stored event; `Offset(0)` starts at the beginning; `Offset(last + 1)` on a caught-up partition waits for the next event and raises no error (also on a hub that was empty); `Timestamp(t)` delivers events enqueued at or after `t` (enqueued times have millisecond resolution) and `Timestamp` an hour ago delivers everything. Without a registered checkpoint `Last` skips events recorded while the process was down and `First` replays the stream on every restart.
  - **Partition state.** An empty partition reports begin and last sequence number `-1`, `IsEmpty` true and a last enqueued time of the Unix epoch; `IsGeoReplicationEnabled` is false. `EventHubsStartOffsetResolver` answered `0` for every kind on an empty partition, `last + 1` for `Last` on a written one, `null` for a `Timestamp` at or before the last event and the tail for a later one.
  - **Checkpoint resume.** With a registered checkpoint (a hand-rolled one and the built-in SQLite store), a restart resumed each partition after its own last processed event and replayed nothing, also when the partition was fully caught up. `Last` on an empty checkpoint was seeded to `last` (`-1` on an empty partition, verified on a partitioned hub where one partition was never written) before any event was read, so events recorded while the process was down were delivered; a `Timestamp` later than the last event seeded the tail, an earlier one logged the warning and stored the position after the first batch; `First` and `Offset(n)` were not seeded.
  - **Retry and halting.** A failing batch was retried in-process on the same events (three invocations with `[RetryPolicy(2, 0)]`) and nothing was written to the event hub. After the retries were exhausted only the partition with the poison batch stopped; the other partitions kept delivering and a critical log was written. With the blob store (load balancing interval 1 s, expiration 8 s) the ownership blobs of halted partitions were still renewed after the expiration had passed, so a halted partition is not given away because its ownership expired. A halted partition is not exempt from rebalancing: an instance joining the consumer group took two of four partitions, and for those the poison batch was delivered again from the stored position on the new owner.
  - **Ownership.** Without a container one instance was assigned all partitions. Two instances sharing a container split four partitions two and two with no overlap (the first instance revoked exactly the partitions the second was assigned); stopping one instance cleanly moved its partitions to the other; with a shared checkpoint 40 events were handled exactly once across two hosts and both handled some. The container held only `.../ownership/{n}` blobs. Killing one of two instances of the sample with `kill -9` (SDK defaults: 30 s load balancing interval, 2 min expiration) moved its partitions to the survivor 106 s later; no reading was lost and five readings of the in-flight batches were handled twice. Two uncoordinated processes without a container were both assigned all four partitions, but each stopped receiving some partitions for periods without an error (in a 40 s run with 160 events one process received 70 and the other 117); `OwnershipLost` was reported about one load balancing interval after the loss and the warning naming the consumer group was logged.
  - **Failures.** A start position resolution that throws from the SDK's `GetCheckpointAsync` did not claim that partition: the exception was reported through `OnProcessingErrorAsync` without a partition (operation "Attempting to claim a new ownership in the storage service."), the delegate was invoked five times within 70 ms (the SDK's retries) and again at the next load balancing cycle, the other partitions were unaffected, and once the store recovered the partition resumed from its stored position with no event lost. With the blob store the ownership blob of that partition was nevertheless recorded as owned by the failing instance. A missing consumer group made `StartProcessingAsync` throw an `AggregateException` with `ResourceNotFound` after about one second, which Flowly rethrows naming the group. A missing event hub made `GetEventHubPropertiesAsync` fail with `ServiceCommunicationProblem` (transient) after about 12 s of SDK retries, whereas sending to it failed with `ResourceNotFound` in 0.5 s; the validator maps both. A wrong declared partition count (fewer than, more than, or none against a partitioned hub), a missing ownership container and a connection string with an `EntityPath` all failed host start with the messages described above. `$Default` could be read.
  - **Waiting partition taken over by another instance.** Two instances sharing a consumer group and an ownership container (load balancing interval 1 s, expiration 8 s, four partitions), the first unable to read the checkpoint for partition 1 (instance A) and the second able to (instance B).
    - Before the ownership listing was observed: A reported `0=Running 1=Waiting 2=Running 3=Running` with the stream health check unhealthy and the state gauge at 1 for partition 1. A's start position resolution for partition 1 ran in every load balancing cycle until B claimed the partition (B was assigned partitions 1 and 3). A then reported the loss of partition 3 only; for partition 1 the SDK raised no stop callback and no error callback, and the resolution was no longer attempted. The entry stayed `Waiting` (health unhealthy, gauge 1) for the 7 min 09 s the run was kept going, while B was healthy and ran the partition. It ended only when B was stopped and the SDK initialized the partition on A again, within the same second as B stopping. When B joined, the SDK picks the partitions it takes at random; B took partitions 0 and 2 in the first start and 1 and 3 in a restart.
    - With the ownership listing observed: B was assigned partitions 1 and 3 at 13:56:46.56, A logged that partition 1 is now owned by another instance 0.4 s later and reported `0=Running 2=Running` (health healthy, gauge 0 for partitions 0 and 2) at its next state sample, 0.8 s after the claim. Partitions 0 and 2, which A runs, stayed `Running` throughout and partition 3 was removed by the SDK's own loss report. With the checkpoint failure removed and B stopped cleanly, A was assigned partitions 1 and 3 again in the same cycle (state `0..3=Running`, health healthy).
    - The opt-in tests `WaitingPartitionOwnershipTests` pass against the emulator; with the observation disabled the first of them times out waiting for the entry to be removed.
  - **Health check (`enableHealthCheck`).** The three opt-in health check tests passed: two existing hubs were `Healthy` and named in the description, a missing hub made the result `Unhealthy` naming only that hub, and a connection string pointing at an address nothing listens on (`127.0.0.1:1`) made it `Unhealthy`. A small ASP.NET Core host with `UseAzureEventHubs(..., enableHealthCheck: true)` and `MapHealthChecks` against a hub `it-single` reported `Healthy` (a `Record` took 0.2 s). Stopping the emulator container (`docker stop`) made the first poll answer `Unhealthy` after 5.0 s, the probe timeout, with the description "did not respond within 5 seconds" and a `TaskCanceledException` as the exception: with the emulator down the SDK call does not fail fast, it is the 5 second timeout that ends the probe. Starting the container again (`docker start`) made the check `Healthy` again 1.7 to 1.9 s after the command returned, and `Record` through the same host succeeded again without restarting it. Fourteen stop and start cycles on two host processes and two emulator instances gave 5.0 s each time and 1.7 to 1.9 s each time (polled every 0.5 s, each poll runs a probe, so the figures are accurate to about that).
  - **Not reproducible on the emulator:** a partition id outside `0..n-1` (the emulator only produces `0..n-1`), the geo-replication warning (the emulator reports it disabled; the warning path is covered by unit tests only).
  - **Not verified (the emulator is a test double: no management plane, a minimum retention of one hour, its own stock quotas of 10 hubs, 20 consumer groups per hub, 32 partitions and 1 MB events):** a real namespace, so also real latencies and throttling; retention floors and what a sequence number below the retention floor does; tier limits (message size, partitions, consumer groups); ARM and RBAC behaviour and Microsoft Entra authentication; geo-replication and what Azure documents about offsets after a failover; whether the service always returns numeric partition ids; partitions added after start; compacted hubs; the `Balanced` load balancing strategy; clusters larger than two instances or four partitions; TLS and private networking; prefetch, memory and throughput.

- **Live observations** (RabbitMQ 4.3.2, `rabbitmq:4-management` with `rabbitmq_stream`, `stream.advertised_host = 127.0.0.1` and `stream.advertised_port` set to the published port, `RabbitMQ.Stream.Client` 1.12.0; one process hosting a 3-partition handler with batches of 5, one retry, a switch that makes the handler throw, and the Management API on the same host; API key authorization):

- **Live observations** (PowerShell 7.6 under `pwsh`, module imported from the Debug build output; one host with RabbitMQ 4.4.0 (`rabbitmq:4-management`), SQLite dead letter tracking, a message handler that failed while a flag file existed, and the Management API with a read and a write API key): three messages were dead-lettered and `Get-FlowlyDeadLetter -Status Pending` listed them; `-Skip 1 -First 1` returned one record; `Submit-FlowlyDeadLetter -WhatIf` made no request (three still pending).

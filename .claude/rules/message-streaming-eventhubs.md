# Azure Event Hubs Message Streaming Conventions

The transport-independent rules are in `message-streaming-conventions.md`. Evidence: `docs/ai/message-streaming-verification.md`.

## Azure Event Hubs

`Flowly.AzureEventHubs` is the stream-only transport (`AzureEventHubsClient` implements `IStreamCapableMessageBusClient`, `IPartitionedStreamCapableMessageBusClient` and `IStreamStartOffsetResolver`, not `IMessageBusClient`). Decided design, do not re-derive it differently:

- **No `IMessagingTopologyCreator` is registered for the provider.** The queue topology creator is optional for a stream-only provider (like the event topology creator): `IMessagingTopologyCreatorRegistry.TryGetCreator` returns `null` and `QueueRegistrarHostedService` skips queue topology creation for it. The provider is still registered with `createTopologyOverride: false`, because validators only run when topology creation is off and `AzureEventHubsTopologyValidator` must always run. A stream topology creator interface and a stream description are not part of the abstractions; they are designed against a stream-only transport that creates topology.
- **The Azure Event Hubs SDK owns partition ownership and rebalancing; Flowly adds no assignment protocol.** Consumption uses the stock `PluggableCheckpointStoreEventProcessor<EventProcessorPartition>` (`EventHubsSdkProcessor`, a one-to-one delegation to `IEventHubsPartitionCallbacks`). Ownership is kept in the stock `BlobCheckpointStore` over the optional `BlobContainerClient partitionOwnershipContainer` of `UseAzureEventHubs`, or in `InMemoryPartitionOwnershipStore` (one per processor, no storage) when none is configured. Flowly never calls `UpdateCheckpointAsync` (the in-memory store throws if anything does); a registered `MessageStreamCheckpoint<T>` is the only source of positions. The SDK's `CheckpointPosition` is not used: the constructor that takes only a sequence number is `[Obsolete]` and the others need a string offset a `long` `StreamOffset` cannot carry, while `EventPosition.FromSequenceNumber` is not obsolete. Keep every position conversion in `EventHubsStartPositions` so a later move to the string offset touches one class.
- **Start positions come through the processor's `GetCheckpointAsync` override**, which returns an `EventProcessorCheckpoint` whose `StartingPosition` is what Flowly resolved (and `null` for the SDK's start-up probe partition id `-1`, which must never reach Flowly's checkpoint). The mapping is `First` to `Earliest`, `Last` to `Latest` (only new events, identical to the other transports), `Timestamp` to `FromEnqueuedTime` (kind `Unspecified` is UTC), and `Offset(n)` to `FromSequenceNumber(n - 1, isInclusive: false)`: the stored position is the last processed sequence number and `ResolveStartPosition` hands back `Offset(stored + 1)`, so resuming is the exclusive form of the stored value. The exclusive form is the one that stays valid on an empty or fully caught-up partition (the inclusive `last + 1` is rejected by the service as beyond the end), and `-1` starts at the first event ever sent. `MessageProperties.StreamOffset` is `EventData.SequenceNumber`; sequence numbers are per partition and start at `0`.
- **Partition ids are mapped as numbers, in one class.** Partition id `"k"` is Flowly partition `k` (`EventHubsPartitionIds`); the startup validator requires the hub's ids to be exactly `0..n-1` for `[StreamPartitions(n)]` and exactly `0` otherwise. A partition id that is not a number below the declared count throws when the SDK reports it.
- **The consumer group is `MessageBusProcessorOptions.ConsumerName`** (the handler's `ConsumerName`, the same value that keys the checkpoint). It must exist on the event hub, `"$Default"` selects the default group, an invalid name (`EventHubsConsumerGroup`) fails at `CreateStreamProcessor`/`CreatePartitionedStreamConsumer` naming it, and a missing group is the SDK's `ResourceNotFound` from `StartProcessingAsync`, rethrown as an `InvalidOperationException` naming the group and the fix.
- **Assigned/revoked mapping.** `EventHubsPartitionedStreamConsumer<T>` resolves the start position once per assignment (the SDK's `GetCheckpointAsync` and `OnInitializingPartitionAsync` calls share it, in either order) before the partition's processor exists and raises `PartitionAssigned` from the initialize callback; a failed resolution is logged and thrown to the SDK, so no loop runs for a partition with an unknown position (the RabbitMQ consumer has the same rule). `ProcessingStoppedReason.OwnershipLost` raises `PartitionRevoked`; `Shutdown` raises nothing because the background service's `StopAsync` already stops the loops. Ownership loss is logged as a warning naming the consumer group when no container is configured (another process reading that group is then possible, and the SDK also reports the loss when reading the partition fails), and as information otherwise. The non-partitioned `EventHubsStreamProcessor<T>` has no logger (`CreateStreamProcessor` takes none) and reports a lost partition through `ProcessError`; when the SDK initializes the partition again it resumes after the last event handed to the handler loop instead of at the original start position.
- **A waiting partition taken over by another instance is revoked from the ownership listing.** The SDK reports no loss for a partition this process never started (its start position resolution threw before the partition was initialized, so there is no `OwnershipLost`, and the error callback arrives without a partition), so the `Waiting` state entry would have no revoke to end it. With a `partitionOwnershipContainer`, `EventHubsProcessorFactory` wraps the `BlobCheckpointStore` handed to the SDK processor in `OwnershipObservingCheckpointStore` and gives the processor an explicit `EventProcessorOptions.Identifier` that the decorator matches against. Every ownership listing of the SDK (one per load balancing cycle) is forwarded unchanged and each partition whose record names another identifier and is not expired (younger than the effective `partitionOwnershipExpiration`) is reported through `IEventHubsPartitionCallbacks.PartitionOwnedByAnotherInstance` (a default interface member, a no-op for the non-partitioned processor, which has no waiting state). An expired record of another instance is ignored: the SDK treats it as free and claims it again, which would only record `Waiting` again. `EventHubsPartitionedStreamConsumer<T>` keeps a set of partitions whose resolution failed (added in the failure path while no processor exists for the partition, cleared by `InitializePartition`, both under its lock) and raises `PartitionRevoked` for a reported partition in the set, once per loss (it leaves the set before the event is raised, and a later failure adds it again). A per-partition gate orders this against assignment: `InitializePartition` holds it from clearing the set until `PartitionAssigned` has returned, and the report takes it without waiting and is skipped when it is busy, to be evaluated again with the next listing, so a processor-less revoke never follows a new assignment of the same partition. In the shared service a revoke for a partition without a loop removes only the `Waiting` entry the service itself recorded (`StreamPartitionStateReporter.Waiting` returns the entry's version, the service keeps the latest per partition and passes it to `IStreamPartitionStateRegistry.Remove(key, expectedVersion)`), so a late revoke cannot delete the entry of a newer assignment; a revoke for a partition with a loop removes the entry unconditionally, as before. Without a container the ownership is kept in process and nothing is observed (instances are not coordinated anyway). Detection takes up to one load balancing cycle after the other instance's claim.
- **Halting keeps ownership.** A halted `StreamPartitionRunner` stays alive and stops taking events, so the awaited `ProcessMessage` delegate does not complete and the Event Hubs batch callback of that partition stays blocked (without advancing anything) until the partition is resumed, lost, the host stops or the SDK cancels the batch; the runner no longer calls `StopProcessing` on the processor for a halt. The SDK keeps renewing the ownership while the callback is blocked, so the partition is not given away because its ownership expired and the other partitions keep running. A halted partition is not exempt from rebalancing: when another instance joins the consumer group, the partitions it is given can include a halted one, which resumes from the stored position on the new owner and delivers the poison batch again (nothing is skipped; both observed on the emulator). A resume of the held batch (see "Halt, don't skip" in message-streaming-conventions.md) releases the blocked callback in place. Only the consumer's revoke, shutdown and stop release a halted callback without a resume, because the background service cancels the runner first. Events are buffered per partition by `StreamPartitionRunner` in a bounded buffer (see "Halt, don't skip" in message-streaming-conventions.md), on top of the SDK prefetch, which is not exposed. The in-place resume was run against the emulator with the blob ownership container: a halted partition resumed through the Management API released the blocked callback and no event was skipped or handled twice (see `docs/ai/message-streaming-verification.md`).
- **`IStreamStartOffsetResolver` reads the partition properties and never answers too high** (`EventHubsStartOffsetResolver`): `Last` is `LastEnqueuedSequenceNumber + 1` (`0` for an empty partition, since the properties then report `-1`), `First` the beginning sequence number (at least `0`), `Offset(n)` is `n`. `Timestamp` cannot be translated into a sequence number without reading events, so it is resolved only when the partition is empty or the time is later than the last enqueued event (then it is the tail, which is not too high: everything later is at or after the time); otherwise it answers `null` and the first-run seeding falls back to storing the position after the first batch. The seed stored for an empty partition is therefore `-1`.
- **Producing.** `Record` uses the service-side Event Hubs partition key, so the partition index a key maps to differs from the client-side FNV-1a of RabbitMQ and InMemory; no key is round robin; a non-partitioned contract ignores the key.
- **Retention is configured on the event hub.** `[StreamRetention]` `MaxLengthBytes` is ignored with a startup warning, `MaxAgeSeconds` is neither applied nor verified (information message).
- **Geo-replication.** The startup validator warns when an event hub reports `IsGeoReplicationEnabled` while any `MessageStreamCheckpoint<T>` is registered in the service collection (after a forced failover the offsets of the same data can differ between regions). The check is deliberately not narrowed to the message types read from that hub. The hub side is exact: the validator reads `IsGeoReplicationEnabled` for each event hub that has a stream registered on the Event Hubs provider, producer-only hubs included. The checkpoint side is host-wide: it only asks whether any `MessageStreamCheckpoint<T>` is registered anywhere in the host, not whether one belongs to a message type read from that event hub. It can therefore warn when no Event Hubs position is stored, for example when the only checkpoint belongs to a RabbitMQ stream handler while a geo-replicated event hub is also used, or when the host only writes to the geo-replicated event hub with `IMessageRecorder`. It never misses the real case, a checkpoint for a handler that reads a geo-replicated event hub, so it errs towards false positives; it is a single startup warning per event hub and never fails startup. It matters only with a registered checkpoint: without one nothing is stored, so there is nothing to go stale, and with one Azure documents that the offsets of the same data can differ between regions after a forced failover. Flowly does not detect or correct this, and the claim rests on Azure documentation, not on a run against the service.
- **Registration tuning.** `loadBalancingInterval` and `partitionOwnershipExpiration` are flat optional parameters of both `UseAzureEventHubs` overloads, validated at registration (`EventHubsOwnershipOptions`): both greater than zero, and the effective expiration (SDK default 2 minutes) greater than the effective interval (SDK default 30 seconds). There is no options delegate. The optional trailing `enableHealthCheck` of both overloads registers `AzureEventHubsHealthCheck` (below).
- **Health check (`enableHealthCheck`).** Registered through `AddHealthChecks()` like the RabbitMQ and Azure Service Bus checks (`TransportRegistrationHelper.BuildHealthCheckName("azure-event-hubs", effectiveName)`, tag `azure-event-hubs`, default failure status). It probes every event hub registered on the provider (the provider's `ProviderQueueManifest` queues that are streams in `StreamQueueManifest`, evaluated on each run because handlers register after the provider) through `IEventHubsInspector.GetEventHubInfo`, the call the topology validator makes, so it exercises connection, credentials and the permission to read hub properties for consuming and producing hosts. The probes run concurrently under one 5 second timeout (`CancellationTokenSource` over a `TimeProvider`); a failed probe, a missing hub or the timeout is `Unhealthy` naming the hubs, there is no `Degraded` for slowness and nothing is cached. A provider without registered hubs reports `Healthy` (nothing to probe). It is independent of `AddMessageStreamHealthCheck` (partition state). The RabbitMQ and Azure Service Bus checks have no timeout of their own (the host's health check timeout applies) and the Service Bus one only opens a TCP connection.
- **Several instances need a registered checkpoint store.** Without one, the configured `StartPosition` is evaluated again for every partition an instance takes over, so `Last` skips the events enqueued while the partition had no owner; a process without a `partitionOwnershipContainer` is not coordinated with another process reading the same consumer group: both are assigned every partition, but each stops receiving some partitions for periods (about one load balancing interval on the emulator) until the SDK reports the loss, so events can be missed. Running more than one instance of a non-partitioned handler against a shared checkpoint store is unsupported, as for RabbitMQ.
- **Unit tests run against fakes of the SDK processor** (`IEventHubsProcessor`, `IEventHubsProcessorFactory`, `IEventHubsInspector`) and stay fully offline.
- **Opt-in emulator tests** live in `tests/Flowly.AzureEventHubs.Tests/Emulator` (namespace `Flowly.AzureEventHubs.Tests.Emulator`) and are skipped, not failed, unless `FLOWLY_EVENTHUBS_EMULATOR_CONNECTION` holds the emulator connection string (the ones that need partition ownership in a blob container additionally need `FLOWLY_EVENTHUBS_EMULATOR_STORAGE_CONNECTION`, the Azurite connection string). The event hubs and consumer groups they use are declared in `Emulator/Config.json`, generated from `EmulatorEntities` (an offline test keeps both in sync), and started with `Emulator/docker-compose.yaml` (`ACCEPT_EULA=Y docker compose up -d`; the emulator has no management plane, so the file is read at container start). Tests wait on observable conditions with a timeout, never on fixed delays.

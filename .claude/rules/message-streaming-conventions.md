# Message Streaming Conventions

## RabbitMQ and InMemory only, no ASB equivalent

`MessageStreamHandler<T>` and `IMessageRecorder` are gated via `IStreamCapableMessageBusClient` (same marker-interface pattern as `IEventCapableMessageBusClient`), checked EAGERLY at registration time (`AddMessageStreamHandler`/`AddMessageRecorder`), not lazily inside a background service like the event marker is. RabbitMQ implements it against real broker-side streams (`x-stream-offset`); `Flowly.InMemory` implements it against an in-process append-only log (`InMemoryStreamLog`) that gives the same log-style, offset-addressable, multi-independent-reader semantics without a broker — see "InMemory streaming" below. `IStreamCapableMessageBusClient` extends `ITransportClient` and does not require `IMessageBusClient`, so a transport can be stream-only (no stream-only transport ships yet); `CreateStreamSender` is its producing-side member, defaulting to `IMessageBusClient.CreateMessageBusSender` so queue-and-stream transports (RabbitMQ, InMemory) need no override while a stream-only transport must override it. The stream registrations resolve their provider with `ProviderNameResolver.Resolve<IStreamCapableMessageBusClient>(...)`, and the stream background services look the client up with `IMessageBusClientRegistry.GetClient<IStreamCapableMessageBusClient>(...)` (the partitioned service uses `GetClient<IPartitionedStreamCapableMessageBusClient>(...)` plus `GetTransportClient(...).MessagingSystem`). Do not add an Azure Service Bus implementation of `IStreamCapableMessageBusClient` unless the underlying transport gains an equivalent replayable-log primitive — ASB has no stream analogue today. A message contract carrying `[StreamPartitions]` additionally requires `IPartitionedStreamCapableMessageBusClient` — see "Partitioned streams" below; both RabbitMQ and InMemory implement it, ASB does not.

## InMemory streaming

`Flowly.InMemory` implements `IStreamCapableMessageBusClient` via `InMemoryStreamLog` — a per-queue, in-process, append-only log with monotonically increasing offsets (not list indices, so retention trimming never renumbers surviving entries). Key semantics, deliberately kept as close to the RabbitMQ behavior as possible so handler code is portable across transports:

- **Independent replay per reader, not competing consumers.** Every `MessageStreamHandler` registration against the same InMemory stream queue gets its own cursor and its own full replay from its own `StartPosition` — exactly like RabbitMQ streams, never a shared/split cursor.
- **No InMemory-specific default retention cap.** If neither `MaxAgeSeconds` nor `MaxLengthBytes` is set, the log grows unbounded — in process memory instead of RabbitMQ's disk — matching RabbitMQ's literal "unbounded unless configured" behavior rather than inventing a second, transport-specific default a developer would need to learn.
- **`MaxLengthBytes` is ignored when `InMemoryOptions.EnableReferencePassing` is enabled.** Reference-passed messages are never serialized, so there is no byte size to account against. Only `MaxAgeSeconds` retention applies in that mode. This must stay documented wherever InMemory streaming or `EnableReferencePassing` is documented — do not silently let this drift out of the docs.
- **No cross-restart persistence, and `MessageStreamCheckpoint<TMessage>` does not change that.** The underlying log itself is gone entirely on process restart — for InMemory there is also no cross-process sharing, unlike RabbitMQ. Persisting a *position* into a durable store would point at stream data that no longer exists after a restart, so the incoherence is structural, not a missing-convenience-store problem. Registering a checkpoint against an InMemory-backed stream throws `InvalidOperationException` at registration time (see "Position persistence via checkpoints" below) rather than being silently accepted as a no-op.
- **Framing for users**: document InMemory streaming primarily as a local development/testing aid, but note it is also a legitimate choice for small, single-instance production deployments (e.g. a self-hosted app on a home server/NAS or a single container) where avoiding external broker infrastructure is the whole point — not "toy/demo only" framing.

## No offset persistence across restarts by default — opt in via checkpoints

By default, `StartPosition` is re-evaluated fresh on every process boot. There is no server-side or database-backed offset checkpoint. `StartPosition.Offset(n)` and `StartPosition.Timestamp(dt)` computed relative to "now" (e.g. `DateTime.UtcNow - TimeSpan.FromHours(2)`) will NOT converge across restarts unless a checkpoint is registered — this is a known limitation of the unconfigured default, not a bug.

### `StartPosition.Last()` means only new messages

`StartPosition.Last()` delivers only messages published after the handler attaches, identically on every transport and on every path. RabbitMQ non-partitioned (`RabbitMqMessageBusClient.CreateStreamProcessor`) sets `x-stream-offset = "next"` and RabbitMQ partitioned (`RabbitMqPartitionedStreamConsumer.OnConsumerUpdate`) returns `OffsetTypeNext`; the `last` specification (and `OffsetTypeLast`) attaches at the last chunk that already exists and delivers the messages in it, so it must not be used for `Last`. InMemory resolves `Last` to the tail offset of the log (`InMemoryStreamLog.ResolveStartOffset`), per partition on a partitioned stream. A new transport maps `Last` the same way. The checkpoint path is unchanged: a stored position resolves to `StartPosition.Offset(stored + 1)` and wins over the configured value, so `Last` is only the bootstrap value when a checkpoint is registered.

### Position persistence via checkpoints

`MessageStreamCheckpoint<TMessage>` (`src/Flowly/MessageStreamCheckpoint.cs`) is the transport-agnostic extension point that restores restart-survival: `InitializeCheckpoint` (called once before the processing loop starts, seeded with `StartPosition` resolved to a concrete offset), `GetStreamPosition` (returns the stored position, or `null` before the first successful batch), and `SaveStreamPosition` (called after each successfully processed batch).

There are two ways to get an implementation registered — both feature-detected via the same DI mechanism, the pattern the Dashboard already uses for Jobs/DeadLetters:

- **Hand-rolled**, against any storage you choose: implement the abstract class yourself and register it, either via plain DI (`services.AddSingleton<MessageStreamCheckpoint<TMessage>, TImpl>()`) or the `AddMessageStreamCheckpoint<TCheckpoint>()` sugar (`src/Flowly/MessageStreamCheckpointRegistrationExtensions.cs`, core `Flowly` — no persistence dependency, infers `TMessage` from `TCheckpoint`'s base type via reflection). See the `add-message-stream-checkpoint` skill.
- **Built-in**, backed by `Flowly.MessageStreams` + a database provider package (`.SqlServer`/`.Postgres`/`.SQLite`): `Add<Provider>MessageStreamPersistence(connection, name?, enableMigrations = true, configure?)` registers a named persistence store (first unnamed registration is the default; a second unnamed registration throws — same "first is default" rule `TransportRegistrationHelper.ResolveProviderName` already enforces for transports, generalized to take a plain `int registeredCount` so both call sites share it), then `UseMessageStreamCheckpoint<TMessage>(name?)` (`Flowly.MessageStreams`) wires an `EfCoreMessageStreamCheckpoint<TMessage>` against it. See the `add-message-stream-persistence` skill.

Key design points, settled deliberately and not to be re-derived differently later:

- **Checkpoint identity is `(ConsumerName, Partition)`, not just the queue.** `ConsumerName` (on `MessageStreamHandlerOptions`, defaults to the handler type name, overridable) disambiguates independent readers of the same stream — without it, two different services replaying the same stream, or horizontally-scaled replicas of one handler, would collide on the same stored position. `Partition` is `null` for a non-partitioned stream. The built-in EF Core store additionally keys on `QueueName` (a checkpoint row also needs to disambiguate message/stream types sharing a `ConsumerName`) and stores `Partition` as a non-nullable `int` with a `-1` sentinel for non-partitioned streams, purely as a storage-layer detail — the public `MessageStreamCheckpointContext.Partition` stays `int?`.
- **RabbitMQ only — InMemory throws at registration, from either entry point.** See "InMemory streaming" above. The guard is checked symmetrically because either registration order is valid (`UseMessageStreamCheckpoint<TMessage>()` can be called before or after `AddMessageStreamHandler<TMessage, THandler>()`): `AddMessageStreamHandler` throws `InvalidOperationException` when a checkpoint is *already* registered against an InMemory-backed provider, and `UseMessageStreamCheckpoint<TMessage>()` throws the same way when the handler is *already* registered against InMemory — each one only catches the case where the other happened first, so both orders are covered. The plain hand-rolled `services.AddSingleton<MessageStreamCheckpoint<T>>()` escape hatch runs no Flowly code at registration, so when it is registered *after* the handler it cannot be caught then; instead both stream background services call `MessageStreamCheckpointHelper.ThrowIfCheckpointRegisteredForInMemory<TMessage>` at the start of `ExecuteAsync` (via `IServiceProviderIsService`, so the checkpoint is never constructed), which throws the same `InvalidOperationException` at host startup before any consumption begins. Topology validators were deliberately not used for this — they only run when `createTopology` is false and are per-transport.
- **Only one live instance per non-partitioned registration.** Flowly does not coordinate exclusive access to a checkpoint store across processes — a generic cross-process lease was considered and rejected as disproportionate scope (TTL tuning, split-brain, heartbeat overhead, no control over the storage engine's concurrency primitives). Running more than one instance of the same non-partitioned handler against a shared checkpoint store is unsupported and will corrupt the stored position. This is a documented constraint, not an enforced one.
- **Duplicate registration of the same handler type in one process still throws** — `AddMessageStreamHandler<TMessage, THandler>()` rejects a second registration of the same `THandler` for the same `TMessage`, independent of whether a checkpoint is involved.
- **The offset a checkpoint persists comes from `MessageProperties.StreamOffset`**, populated per-transport (RabbitMQ from the `x-stream-offset` delivery header, InMemory from the log's per-entry offset) — `null` for non-stream deliveries. A batch is only checkpointed when its last message carries one.
- **Implementations must be thread-safe.** Flowly always resolves the checkpoint via DI as documented (`AddSingleton`), so one instance is shared for the process lifetime. `MessageStreamCheckpointHelper` never calls a checkpoint method twice concurrently for the same `(ConsumerName, Partition)` pair — but for a partitioned stream, `PartitionedMessageStreamProcessingBackgroundService` runs one independent `StreamPartitionRunner` per owned partition (`StreamPartitionRunner.cs`), and every one of those loops calls into the *same* checkpoint instance. `InitializeCheckpoint`/`GetStreamPosition` for a newly-assigned partition (fired from RabbitMQ's `ConsumerUpdateListener`, `RabbitMqPartitionedStreamConsumer.cs` — serialized only within the same partition, never across partitions) can run concurrently with `SaveStreamPosition` for an already-running partition, and `SaveStreamPosition` calls across different partitions' loops run concurrently with each other. This is why the example in `README.md` and the `add-message-stream-checkpoint` skill inject `IDbContextFactory<T>` rather than a `DbContext` directly — a `DbContext` captured as constructor-injected instance state on a singleton is both a DI captive-dependency bug (it's normally `Scoped`) and not thread-safe for the concurrent calls above. `EfCoreMessageStreamCheckpoint<TMessage>` (the built-in implementation) follows this same rule, holding an `IDbContextFactory<MessageStreamCheckpointDataContext>` rather than a `DbContext`.
- **OpenTelemetry instrumentation lives in `MessageStreamCheckpointHelper`, not in any specific `MessageStreamCheckpoint<T>` implementation.** `flowly.message.checkpoint.saved`/`.save.failed`/`.resolved` (tagged `outcome=resumed|fresh`) are recorded at the one call site every checkpoint — built-in or hand-rolled — already passes through, so a hand-rolled checkpoint gets the same telemetry for free. Do not duplicate this instrumentation inside `EfCoreMessageStreamCheckpoint<T>` or any future built-in implementation.
- **Operational reset tooling**: `flowly message-stream list-checkpoints|reset-checkpoint` (`Flowly.Tool`, connects directly to the checkpoint database by connection string) and the Flowly Management API's `message-streams/checkpoints` list/reset actions (`Flowly.ManagementApi`, HTTP, feature-detected when a store is configured) both read/write through the same `MessageStreamCheckpointAdmin` helper in `Flowly.MessageStreams` — do not duplicate this logic a third time. Resetting a position only takes effect on that handler's next process restart, regardless of which tool wrote the row, since `StartPosition` is resolved once at boot.

Any future offset-persistence work beyond this (e.g. cross-process coordination for non-partitioned streams) must be a deliberate, separately-designed feature — do not bolt it on as a side effect of an unrelated change. Partitioned streams have their own persistence story — see "Partitioned streams" below.

## Partitioned streams

A stream can be divided into `N` independent, ordered sub-logs via `[StreamPartitions(count)]` on the message contract (`src/Flowly/StreamPartitionsAttribute.cs`) — mirrors `[StreamRetention]`/`[QueueName]` living on the contract, not the handler. This is additive: a non-partitioned `MessageStreamHandler<T>`/`IMessageRecorder` is completely unaffected by this feature existing.

- **`IPartitionedStreamCapableMessageBusClient` is the delegation-model capability interface** (`src/Flowly/Transport/IPartitionedStreamCapableMessageBusClient.cs`), checked eagerly at registration time like `IStreamCapableMessageBusClient`. Flowly does **not** implement its own cross-instance partition-assignment/rebalancing protocol — that's entirely the transport's job, using whatever native mechanism it has. Flowly's role is limited to running one independent `StreamPartitionRunner` per partition currently owned by this process, reacting to `IPartitionedStreamConsumer<TMessage>.PartitionAssigned`/`PartitionRevoked` as the transport reports them. Do not add partition-ownership coordination logic to core Flowly — it belongs in the transport adapter.
- **Batches never mix partitions.** Each owned partition gets its own `IMessageBusProcessor<TMessage>`, its own accumulate-batch loop, and its own halt-on-exhausted-retries — a poisoned partition halts only that partition; other partitions and the service itself keep running. `IMessageStreamContext<T>.Partition` tells the handler which partition a batch came from (`null` for non-partitioned streams).
- **`StreamPartitionRunner` is shared** between the non-partitioned (`MessageStreamProcessingBackgroundService`, one runner, `partition: null`) and partitioned (`PartitionedMessageStreamProcessingBackgroundService`, one runner per owned partition) background services — this is where the accumulate/retry/halt/checkpoint-save logic actually lives. Do not duplicate this logic when adding a new transport; extend `IMessageBusProcessor<TMessage>`/`IPartitionedStreamConsumer<TMessage>` instead.
- **Checkpointing composes unchanged.** `MessageStreamCheckpointHelper.ResolveStartPosition`/`SaveStreamPositionIfPresent` (shared by both background services) already key on `(ConsumerName, Partition)` — partitioned streams just supply a non-null `Partition`. For a newly-assigned partition, resolving the start position happens through the same `resolveStartPosition` delegate passed into `CreatePartitionedStreamConsumer`, called once per partition the first time this process becomes responsible for it.
- **Producer-side partition routing is a plain send-time concern, not a new sender abstraction.** `MessageProperties.PartitionKey` (set via `IMessageRecorder.Record(message, cancellationToken, partitionKey)` — deliberately placed *after* `cancellationToken`, not before, so existing positional `Record(message, ct)` call sites keep compiling) is resolved to a partition index by each transport's existing `IMessageBusSender` implementation, checking `StreamQueueManifest.GetPartitionCount(queueName)` at send time. No key routes round-robin; a key hashes consistently to the same partition every time. Do not introduce a separate "partitioned sender" interface — this reuses `IMessageBusSender.SendMessage` unchanged.

### InMemory partitioned streams — parity and local development, not scale

`InMemoryPartitionedStreamConsumer` assigns every partition immediately and permanently at `StartProcessingMessages` — `PartitionRevoked` is never raised, since InMemory is single-process by construction and there is no cross-instance ownership to hand off. Each partition is backed by its own `InMemoryStreamLog`, keyed internally as `{queueName}::{partition}` (see `InMemoryBroker.GetOrCreatePartitionedStreamLog`) — reuses the existing unpartitioned log implementation unchanged, just one instance per partition instead of one per queue. This exists so partition-aware handler code (routing, per-partition ordering, `[StreamPartitions]` wiring) can be developed and tested without a real broker — it gets none of the cross-instance throughput benefit partitioning exists for on RabbitMQ, because a single process can't offer that regardless of transport.

### RabbitMQ Super Streams

- **Topology (the exchange + per-partition streams + bindings) is declared over plain AMQP** — `RabbitMqMessagingTopologyCreator.DeclarePartitionedStreamTopology` creates a direct exchange named after the queue, one stream queue per partition named `{queueName}-{partition}` (declared via the same `DeclareStreamQueue` a non-partitioned stream uses), and binds each partition stream to the exchange with the partition index as the routing key. This matches how a Super Stream can be created with any AMQP 0.9.1 client, not just the RabbitMQ Stream protocol client — no new dependency needed just to provision the topology.
- **Producing uses the same plain-AMQP path** — `RabbitMqMessageBusSender` publishes to the partitioned queue's exchange with the resolved partition index as the routing key instead of publishing directly to a queue via the default exchange. No Stream protocol client involvement on the producer side at all.
- **Consuming needs the RabbitMQ Stream protocol client** (`RabbitMQ.Stream.Client` NuGet package, `RabbitMqPartitionedStreamConsumer`) — this is the one piece that genuinely can't be done over AMQP: broker-coordinated Single Active Consumer rebalancing. The client's `ConsumerConfig` (`RabbitMQ.Stream.Client.Reliable` namespace, not the bare `RabbitMQ.Stream.Client` namespace) is configured with `IsSuperStream = true, IsSingleActiveConsumer = true`; its `ConsumerUpdateListener` callback (`(reference, stream, isActive) => Task<IOffsetType>`) is both the ownership-change signal (`isActive` toggling maps to `PartitionAssigned`/`PartitionRevoked`) and where the resume offset for a newly-active partition is resolved — this is also where a registered `MessageStreamCheckpoint<TMessage>` gets consulted, per partition, threading Flowly's own checkpoint straight into the broker's native rebalancing protocol rather than needing the client's own (Blob-Storage-style, for other clients) checkpoint mechanism.
- **The Stream protocol uses a separate port from AMQP** (5552 by default, vs. AMQP's 5672) on the same host — `RabbitMqConnectionPool.GetStreamSystem` derives a `StreamSystemConfig` from the same connection URI already used for AMQP, resolving the endpoint via `RabbitMqConnectionPool.ResolveStreamEndpoint` (host from the URI, port from the `streamPort` constructor parameter). The port is configurable via `UseRabbitMq(..., streamPort: <port>)` — a plain trailing optional `int streamPort = 5552` parameter on `UseRabbitMq`, threaded through `RegisterRabbitMq` into `new RabbitMqConnectionPool(uri, streamPort)`; this deliberately matches the existing flat-optional-parameter convention rather than introducing a `RabbitMqOptions` aggregate. Host scope stays fixed to the AMQP connection's host — no independent stream-host override, since RabbitMQ's stream protocol is always a second port on the same broker host. Any deployment target must publish whichever port is configured on the same host as the AMQP connection — both `flowlyapp`'s `docker-compose.yml` (`5552:5552`, conditioned on `UseRabbitMqStreamPartitions`) and the `flowlyaspireapp` AppHost (`.WithEndpoint(name: "stream", port: 5552, targetPort: 5552)`, conditioned on the same symbol) still default to the standard port 5552 — the templates do not expose a CLI flag for this; a user who changes their deployment's published stream port passes the matching `streamPort:` value to `UseRabbitMq` directly.
- **Partition index is recovered from the source stream name by convention**, not queried from the broker — `RabbitMqPartitionedStreamConsumer` parses `{queueName}-{partition}` directly out of the `sourceStream` argument the client's `MessageHandler` callback provides, rather than calling `StreamSystem.QueryPartition` to cross-check per-message. `QueryPartition` is used elsewhere, at startup — see the next bullet.
- **Declared partition count is validated against the broker at startup, only when `createTopology: false`.** `RabbitMqPartitionedStreamTopologyValidator` — a dedicated `IMessagingTopologyValidator` registered alongside `RabbitMqRetryTopologyValidator`, not folded into it — calls `IRabbitMqConnectionPool.QueryStreamPartitions` (a thin wrapper over `StreamSystem.QueryPartition`) for every queue `StreamQueueManifest.GetPartitionCount` reports as partitioned, and throws `InvalidOperationException` when the broker's actual partition stream count doesn't match the contract's `[StreamPartitions(n)]`. Left unchecked, a mismatch lets `RabbitMqMessageBusSender.ResolvePartition` compute routing keys with no matching exchange binding — publishes silently dropped, no broker error — or leaves real broker partitions permanently unconsumed, since the consumer only reacts to whatever the broker reports and never cross-checks the declared count itself. This deliberately mirrors `createTopology: false`'s existing retry-queue validation instead of introducing a new invocation point: `QueueRegistrarHostedService` runs *every* `IMessagingTopologyValidator` matching a provider (not just the first), so a second validator composes for free. The check does **not** run when `createTopology: true` — that path is additive (declares missing partition streams/bindings) and does not reconcile a broker left with *more* partitions than currently declared (e.g. after lowering `[StreamPartitions(n)]` without recreating the topology); catching that drift as well was explicitly scoped out, not an oversight.
- **Behaviour verified against a live broker.** Verified against RabbitMQ 4.3.2 (the `rabbitmq:4-management` image with the `rabbitmq_stream` plugin) and `RabbitMQ.Stream.Client` 1.12.0, with several OS processes of one partitioned handler sharing a built-in SQLite checkpoint store, on a 12-partition and a 3-partition stream:
  - **Ownership.** `ConsumerUpdateListener` fires with `isActive: true` for every partition when a single instance runs. When a second instance joins, the broker sends `isActive: false` to the first instance for exactly the partitions that move and `isActive: true` to the joiner; the broker reports one `single_active` and one `waiting` consumer per partition stream. A gracefully stopped instance sends nothing for its own partitions — the survivor receives `isActive: true` — and a killed instance's partitions move to the survivor immediately. Restarting the instance moves a share back.
  - **`isActive: false`.** The callback fires reliably, and the offset returned for it is ignored: returning an arbitrary offset for every revoked partition changed nothing for either instance, and the later `isActive: true` call returned the resolved start position, which was honoured. The consumer returns `OffsetTypeFirst` for it.
  - **No revoke after a lost connection.** When the broker restarts, the client recovers each subscription and reports `isActive: true` again without a preceding `isActive: false`, so a partition can be assigned while this process still holds a processing loop for it. `RabbitMqPartitionedStreamConsumer.OnConsumerUpdate` revokes the live loop first and waits for every earlier revocation of that partition before it starts a new loop.
  - **Start position resolution failure.** When `resolveStartPosition` throws inside `ConsumerUpdateListener` (a checkpoint store outage was simulated for one partition of a 3-partition stream), the client does not propagate the exception and logs nothing; it subscribes that partition at its own default offset, `next`, ignoring the configured or stored start position, and the other partitions are unaffected. `RabbitMqPartitionedStreamConsumer.OnConsumerUpdate` therefore resolves the start position first, before registering the partition's processor and raising `PartitionAssigned`, and logs and rethrows a failure. No processing loop exists for that partition afterwards, no checkpoint is saved for it, and the messages the client still delivers for it are dropped with the "not currently processing" warning. Resolving after the loop had started made the loop consume from the client's default offset, so a stored position was ignored without any log entry and later saves would move the checkpoint past the unprocessed backlog.
  - **Checkpoint resume.** After a restart each partition resumes at its stored position plus one (`StartPosition.Offset(saved + 1)`); nothing is replayed when nothing new was published. Graceful stop, `kill -9` and a broker restart lost no message. When a batch was in flight (handler effect visible, checkpoint not yet saved) at a `kill -9`, or at a rebalance, the new owner replayed exactly that batch: duplicates are bounded by one batch per affected partition.
  - **Partition index.** `{queueName}-{partition}` parsed from the source stream name matched the broker for every partition of a 12-partition stream, including 10 and 11: per-partition handled counts equalled the per-stream message counts on the broker.
  - **Start position.** Without a checkpoint, `First` replays every partition, `Offset(n)` applies `n` to each partition's own offset numbering, and `Timestamp(t)` delivers the messages published at or after `t` (the broker resolves timestamps at chunk granularity). `Last` is mapped to the stream protocol's `next` offset (`OffsetTypeNext`), so messages already in any partition are not delivered. The AMQP `last` and the stream protocol's `last` attach at the last chunk and would deliver the messages in it, so they must not be used for `Last`. With a checkpoint, `StartPosition` applies only until the first batch of that `(ConsumerName, Partition)` has been saved; afterwards the stored position wins regardless of the configured value, and messages published while the process was down are delivered. A restart before any batch was processed (for example `Last` on an empty stream) re-evaluates `StartPosition`.
  - **Topology.** With `createTopology: true` the direct exchange, the `{queue}-{n}` streams (`x-queue-type: stream`, retention arguments applied) and the bindings with the partition index as routing key are created as described above. A Super Stream created with `rabbitmq-streams add_super_stream` is consumed and published to by Flowly unchanged. With `createTopology: false`, `RabbitMqPartitionedStreamTopologyValidator` fails host startup both when the Super Stream is missing and when the broker's partition count differs from the one the contract declares.
  - **Stream port.** A wrong `streamPort` fails host startup with `StreamSystemInitialisationException` ("no endpoints could be reached"). The configured endpoint is used for the initial connection and for stream metadata only; the connection that consumes goes to the `stream.advertised_host`/`stream.advertised_port` the broker reports for the partition's leader, except when the configured host is loopback, where the client keeps the configured endpoint. Against a non-loopback host, a broker that advertises an address the client cannot reach (for example the in-container port behind a published port mapping) fails host startup with "None of the brokers could be reached"; with the advertised host and port set to the reachable values the consumer connects. Flowly passes a single endpoint and no address resolver, so a load balancer in front of the stream port is not supported.
  - **Broker restart.** Restarting the broker while two instances consume: the client recovers all subscriptions on its own, consumption resumes, and messages published afterwards are delivered without loss or duplication.

  Not verified: the client's documented statements that the listener runs on the connection's socket thread and that the broker closes the connection when the callback takes longer than 60 seconds (the wait for a pending revocation of the same partition happens inside that callback), clusters with more than one node (leader moves, replica reads), TLS on the stream port, RabbitMQ 3.x and other 4.x versions, other `RabbitMQ.Stream.Client` versions, more than 12 partitions, and instances that stay unreachable for longer than the client's reconnect attempts.

Any future ambiguity in this sub-area (dynamic partition count changes, consumer-group semantics beyond Single Active Consumer, cross-broker partition rebalancing tuning, reconciling broker drift when `createTopology: true`, etc.) still falls under "Ask, don't assume" below.

## Halt, don't skip, on exhausted retries

When in-process retries for a batch are exhausted, `MessageStreamProcessingBackgroundService` stops consuming that queue entirely — it does not advance past the offset and does not skip to the next message. This is surfaced as a critical log entry plus `IHandlerInstrumentation.RecordHalted` telemetry. Do not "fix" a stuck stream by making the service skip past a poison batch — that silently loses data from an append-only log in a way that cannot be undone. Dead-letter-style durable/operator-resolvable recovery for stuck stream messages is an explicit future follow-up, out of scope today.

## In-process retry, not requeue

Stream retries are a plain in-memory loop over the already-received batch, NOT a re-publish to the queue (unlike `MessageProcessingBackgroundService.RepublishForRetry` / `BatchProcessingBackgroundService.RepublishBatchForRetry`). Requeuing into an immutable, replayable stream would permanently corrupt it with retry noise for every future consumer reading from `StartPosition.First()`. Not advancing the offset is itself the retry mechanism — do not add a republish path to `MessageStreamProcessingBackgroundService`.

## Ask, don't assume

Any future ambiguity in this feature area (new retention knobs, offset persistence, cross-transport support, dead-letter recovery for halted streams, consumer-group semantics, etc.) must be resolved by asking rather than assuming — mirroring the design process that produced this feature. Do not guess at a shape for a new stream-related API surface and ship it; confirm with the user first.

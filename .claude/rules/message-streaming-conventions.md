# Message Streaming Conventions

Transport-specific rules: `message-streaming-rabbitmq.md` (Super Streams, offset probe, start position recovery) and `message-streaming-eventhubs.md`, each loaded when you work in that transport.

Records of the live-broker and emulator runs behind these rules (versions, figures, scenarios, what was not verified) live in `docs/ai/message-streaming-verification.md`, which is not loaded automatically; read it before changing the behaviour it covers.

## Stream-capable transports only (RabbitMQ, InMemory and Azure Event Hubs ship today), no ASB equivalent

`MessageStreamHandler<T>` and `IMessageRecorder` are gated via `IStreamCapableMessageBusClient` (same marker-interface pattern as `IEventCapableMessageBusClient`), checked EAGERLY at registration time (`AddMessageStreamHandler`/`AddMessageRecorder`), not lazily inside a background service like the event marker is. RabbitMQ implements it against real broker-side streams (`x-stream-offset`); `Flowly.InMemory` implements it against an in-process append-only log (`InMemoryStreamLog`) that gives the same log-style, offset-addressable, multi-independent-reader semantics without a broker — see "InMemory streaming" below. `IStreamCapableMessageBusClient` extends `ITransportClient` and does not require `IMessageBusClient`, so a transport can be stream-only (`Flowly.AzureEventHubs` is the stream-only transport, see `message-streaming-eventhubs.md`); `CreateStreamSender` is its producing-side member, defaulting to `IMessageBusClient.CreateMessageBusSender` so queue-and-stream transports (RabbitMQ, InMemory) need no override while a stream-only transport must override it. The stream registrations resolve their provider with `ProviderNameResolver.Resolve<IStreamCapableMessageBusClient>(...)` — a stream contract without `[ProviderAffinity]` routes to the first registered provider that supports streams, wherever it sits in the registration order relative to queue-only providers, and explicit affinity to a provider without stream support throws — and the stream background services look the client up with `IMessageBusClientRegistry.GetClient<IStreamCapableMessageBusClient>(...)` (the partitioned service uses `GetClient<IPartitionedStreamCapableMessageBusClient>(...)` plus `GetTransportClient(...).MessagingSystem`). Do not add an Azure Service Bus implementation of `IStreamCapableMessageBusClient` unless the underlying transport gains an equivalent replayable-log primitive — ASB has no stream analogue today. A message contract carrying `[StreamPartitions]` additionally requires `IPartitionedStreamCapableMessageBusClient` — see "Partitioned streams" below; RabbitMQ, InMemory and Azure Event Hubs implement it, ASB does not.

## InMemory streaming

`Flowly.InMemory` implements `IStreamCapableMessageBusClient` via `InMemoryStreamLog` — a per-queue, in-process, append-only log with monotonically increasing offsets (not list indices, so retention trimming never renumbers surviving entries). Key semantics, deliberately kept as close to the RabbitMQ behavior as possible so handler code is portable across transports:

- **Independent replay per reader, not competing consumers.** Every `MessageStreamHandler` registration against the same InMemory stream queue gets its own cursor and its own full replay from its own `StartPosition` — exactly like RabbitMQ streams, never a shared/split cursor.
- **No InMemory-specific default retention cap.** If neither `MaxAgeSeconds` nor `MaxLengthBytes` is set, the log grows unbounded — in process memory instead of RabbitMQ's disk — matching RabbitMQ's literal "unbounded unless configured" behavior rather than inventing a second, transport-specific default a developer would need to learn.
- **`MaxLengthBytes` is ignored when `InMemoryOptions.EnableReferencePassing` is enabled.** Reference-passed messages are never serialized, so there is no byte size to account against. Only `MaxAgeSeconds` retention applies in that mode. This must stay documented wherever InMemory streaming or `EnableReferencePassing` is documented — do not silently let this drift out of the docs.
- **No cross-restart persistence, and `MessageStreamCheckpoint<TMessage>` does not change that.** The underlying log itself is gone entirely on process restart — for InMemory there is also no cross-process sharing, unlike RabbitMQ. Persisting a *position* into a durable store would point at stream data that no longer exists after a restart, so the incoherence is structural, not a missing-convenience-store problem. Registering a checkpoint against an InMemory-backed stream throws `InvalidOperationException` at registration time (see "Position persistence via checkpoints" below) rather than being silently accepted as a no-op.
- **Framing for users**: document InMemory streaming primarily as a local development/testing aid, but note it is also a legitimate choice for small, single-instance production deployments (e.g. a self-hosted app on a home server/NAS or a single container) where avoiding external broker infrastructure is the whole point — not "toy/demo only" framing.

## ConsumerName reaches the transport

Both stream background services pass the resolved `ConsumerName` (`MessageStreamHandlerOptions.ConsumerName`, defaulting to the handler type name, resolved once in `MessageStreamHandlerOptionsResolver` into the handler settings) to the transport as `MessageBusProcessorOptions.ConsumerName` when they call `IStreamCapableMessageBusClient.CreateStreamProcessor` or `IPartitionedStreamCapableMessageBusClient.CreatePartitionedStreamConsumer`. It is the very value that keys a registered checkpoint, so the transport and the checkpoint store always agree on the identity of a reader. A transport may use it to identify the reader on the broker, for example as a broker-side consumer group: Azure Event Hubs uses it as the consumer group, RabbitMQ and InMemory ignore it. It is an additive init property, so the positional constructor is unchanged. Do not compute a second consumer name anywhere — read it from the handler settings.

## No offset persistence across restarts by default — opt in via checkpoints

By default, `StartPosition` is re-evaluated fresh on every process boot. There is no server-side or database-backed offset checkpoint. `StartPosition.Offset(n)` and `StartPosition.Timestamp(dt)` computed relative to "now" (e.g. `DateTime.UtcNow - TimeSpan.FromHours(2)`) will NOT converge across restarts unless a checkpoint is registered — this is a known limitation of the unconfigured default, not a bug. With a registered checkpoint the first run's position is fixed up front, see "First-run seeding" below.

### `StartPosition.Last()` means only new messages

`StartPosition.Last()` delivers only messages published after the handler attaches, identically on every transport and on every path. RabbitMQ non-partitioned (`RabbitMqMessageBusClient.CreateStreamProcessor`) sets `x-stream-offset = "next"` and RabbitMQ partitioned (`RabbitMqPartitionedStreamConsumer.OnConsumerUpdate`) returns `OffsetTypeNext`; the `last` specification (and `OffsetTypeLast`) attaches at the last chunk that already exists and delivers the messages in it, so it must not be used for `Last`. InMemory resolves `Last` to the tail offset of the log (`InMemoryStreamLog.ResolveStartOffset`), per partition on a partitioned stream. Azure Event Hubs maps `Last` to `EventPosition.Latest`. A new transport maps `Last` the same way. The checkpoint path is unchanged: a stored position resolves to `StartPosition.Offset(stored + 1)` and wins over the configured value, so `Last` is only the bootstrap value when a checkpoint is registered. The offset a transport reports as the start of `Last` (`IStreamStartOffsetResolver`, see "First-run seeding") is the same "next" offset these mappings attach at: the highest existing offset plus one, `0` on an empty stream. Do not define "next" a second time.

### Position persistence via checkpoints

`MessageStreamCheckpoint<TMessage>` (`src/Flowly/MessageStreamCheckpoint.cs`) is the transport-agnostic extension point that restores restart-survival: `InitializeCheckpoint` (called once before the processing loop starts, receives only the reader identity), `GetStreamPosition` (returns the stored position, or `null` when neither a processed batch nor a bootstrap seed has been saved), and `SaveStreamPosition` (called after each successfully processed batch, and once before consumption starts to seed the first run's position).

There are two ways to get an implementation registered — both feature-detected via the same DI mechanism, the pattern the Dashboard already uses for Jobs/DeadLetters:

- **Hand-rolled**, against any storage you choose: implement the abstract class yourself and register it, either via plain DI (`services.AddSingleton<MessageStreamCheckpoint<TMessage>, TImpl>()`) or the `AddMessageStreamCheckpoint<TCheckpoint>()` sugar (`src/Flowly/MessageStreamCheckpointRegistrationExtensions.cs`, core `Flowly` — no persistence dependency, infers `TMessage` from `TCheckpoint`'s base type via reflection). See the `add-message-stream-checkpoint` skill.
- **Built-in**, backed by `Flowly.MessageStreams` + a database provider package (`.SqlServer`/`.Postgres`/`.SQLite`): `Add<Provider>MessageStreamPersistence(connection, name?, enableMigrations = true, configure?)` registers a named persistence store (first unnamed registration is the default; a second unnamed registration throws — same "first is default" rule `TransportRegistrationHelper.ResolveProviderName` already enforces for transports, generalized to take a plain `int registeredCount` so both call sites share it), then `UseMessageStreamCheckpoint<TMessage>(name?)` (`Flowly.MessageStreams`) wires an `EfCoreMessageStreamCheckpoint<TMessage>` against it. See the `add-message-stream-persistence` skill.

Key design points, settled deliberately and not to be re-derived differently later:

- **Checkpoint identity is `(ConsumerName, Partition)`, not just the queue.** `ConsumerName` (on `MessageStreamHandlerOptions`, defaults to the handler type name, overridable) disambiguates independent readers of the same stream — without it, two different services replaying the same stream, or horizontally-scaled replicas of one handler, would collide on the same stored position. `Partition` is `null` for a non-partitioned stream. The built-in EF Core store additionally keys on `QueueName` (a checkpoint row also needs to disambiguate message/stream types sharing a `ConsumerName`) and stores `Partition` as a non-nullable `int` with a `-1` sentinel for non-partitioned streams, purely as a storage-layer detail — the public `MessageStreamCheckpointContext.Partition` stays `int?`.
- **Every stream transport except InMemory — InMemory throws at registration, from either entry point.** RabbitMQ and Azure Event Hubs support checkpoints; the built-in EF Core store and `MessageStreamCheckpointHelper` hold no transport-specific code, and the offset they persist is whatever `MessageProperties.StreamOffset` the transport sets (Azure Event Hubs: the event's sequence number in its partition). See "InMemory streaming" above. The guard is checked symmetrically because either registration order is valid (`UseMessageStreamCheckpoint<TMessage>()` can be called before or after `AddMessageStreamHandler<TMessage, THandler>()`): `AddMessageStreamHandler` throws `InvalidOperationException` when a checkpoint is *already* registered against an InMemory-backed provider, and `UseMessageStreamCheckpoint<TMessage>()` throws the same way when the handler is *already* registered against InMemory — each one only catches the case where the other happened first, so both orders are covered. The plain hand-rolled `services.AddSingleton<MessageStreamCheckpoint<T>>()` escape hatch runs no Flowly code at registration, so when it is registered *after* the handler it cannot be caught then; instead both stream background services call `MessageStreamCheckpointHelper.ThrowIfCheckpointRegisteredForInMemory<TMessage>` at the start of `ExecuteAsync` (via `IServiceProviderIsService`, so the checkpoint is never constructed), which throws the same `InvalidOperationException` at host startup before any consumption begins. Topology validators were deliberately not used for this — they only run when `createTopology` is false and are per-transport.
- **Only one live instance per non-partitioned registration.** Flowly does not coordinate exclusive access to a checkpoint store across processes — a generic cross-process lease was considered and rejected as disproportionate scope (TTL tuning, split-brain, heartbeat overhead, no control over the storage engine's concurrency primitives). Running more than one instance of the same non-partitioned handler against a shared checkpoint store is unsupported and will corrupt the stored position. This is a documented constraint, not an enforced one.
- **Duplicate registration of the same handler type in one process still throws** — `AddMessageStreamHandler<TMessage, THandler>()` rejects a second registration of the same `THandler` for the same `TMessage`, independent of whether a checkpoint is involved.
- **The offset a checkpoint persists comes from `MessageProperties.StreamOffset`**, populated per-transport (RabbitMQ from the `x-stream-offset` delivery header, InMemory from the log's per-entry offset) — `null` for non-stream deliveries. A batch is only checkpointed when its last message carries one.
- **Implementations must be thread-safe.** Flowly always resolves the checkpoint via DI as documented (`AddSingleton`), so one instance is shared for the process lifetime. `MessageStreamCheckpointHelper` never calls a checkpoint method twice concurrently for the same `(ConsumerName, Partition)` pair — but for a partitioned stream, `PartitionedMessageStreamProcessingBackgroundService` runs one independent `StreamPartitionRunner` per owned partition (`StreamPartitionRunner.cs`), and every one of those loops calls into the *same* checkpoint instance. `InitializeCheckpoint`/`GetStreamPosition` for a newly-assigned partition (fired from RabbitMQ's `ConsumerUpdateListener`, `RabbitMqPartitionedStreamConsumer.cs` — serialized only within the same partition, never across partitions) can run concurrently with `SaveStreamPosition` for an already-running partition, and `SaveStreamPosition` calls across different partitions' loops run concurrently with each other. This is why the example in `README.md` and the `add-message-stream-checkpoint` skill inject `IDbContextFactory<T>` rather than a `DbContext` directly — a `DbContext` captured as constructor-injected instance state on a singleton is both a DI captive-dependency bug (it's normally `Scoped`) and not thread-safe for the concurrent calls above. `EfCoreMessageStreamCheckpoint<TMessage>` (the built-in implementation) follows this same rule, holding an `IDbContextFactory<MessageStreamCheckpointDataContext>` rather than a `DbContext`.
- **OpenTelemetry instrumentation lives in `MessageStreamCheckpointHelper`, not in any specific `MessageStreamCheckpoint<T>` implementation.** `flowly.message.checkpoint.saved`/`.save.failed`/`.resolved` (tagged `outcome=resumed|fresh`) are recorded at the one call site every checkpoint — built-in or hand-rolled — already passes through, so a hand-rolled checkpoint gets the same telemetry for free. Do not duplicate this instrumentation inside `EfCoreMessageStreamCheckpoint<T>` or any future built-in implementation.
- **Operational reset tooling**: `flowly message-stream list-checkpoints|reset-checkpoint` (`Flowly.Tool`, connects directly to the checkpoint database by connection string) and the Flowly Management API's `message-streams/checkpoints` list/reset actions (`Flowly.ManagementApi`, HTTP, feature-detected when a store is configured) both read/write through the same `MessageStreamCheckpointAdmin` helper in `Flowly.MessageStreams` — do not duplicate this logic a third time. Resetting a position only takes effect on that handler's next process restart, regardless of which tool wrote the row, since `StartPosition` is resolved once at boot.

### First-run seeding

When a checkpoint is registered and `GetStreamPosition` returns `null`, `MessageStreamCheckpointHelper.ResolveStartPosition` fixes the first run's position before consumption starts, so a restart before the first batch (for example `Last` on an empty stream, messages published while the process was down) does not move it. Decided design, do not re-derive it differently:

- **Seed through the existing `SaveStreamPosition`.** The helper saves `resolved start offset - 1` (the stored value stays "last processed", resume at `+1`, so `-1` is a legal stored value meaning "start at offset 0") with an additive `MessageStreamCheckpointSaveContext.IsBootstrapSeed = true`, then returns `StartPosition.Offset(resolved)`. Hand-written checkpoints keep compiling and behaving and gain the fix; the built-in EF store already upserts a nullable `Position`, so it needs no schema change or migration. A store must accept negative positions and must not treat every save as a handled batch.
- **A seed never overwrites a stored position.** A save with `IsBootstrapSeed = true` writes only when no position is stored for `(ConsumerName, Partition)` (a row that `InitializeCheckpoint` created without a position counts as none stored) and does nothing otherwise, as one atomic conditional operation, not a read followed by a write. A seed can complete late, after a later resolution attempt succeeded and the runner saved a higher position (an abandoned start position resolution whose resolver or store ignores cancellation), and an unconditional write moves the position backwards, so the next restart replays everything in between. The contract is stated on `MessageStreamCheckpoint<T>.SaveStreamPosition` and `IsBootstrapSeed`. A save without the flag always overwrites.
- **Two layers.** (1) The built-in `EfCoreMessageStreamCheckpoint<T>` implements it for every backend through the shared store: an `ExecuteUpdate` that requires a null position, then an insert whose unique key (`QueueName`, `ConsumerName`, `Partition`) conflict is a no-op when the row exists (a `DbUpdateException` with no row present is rethrown), followed by one more conditional update for the row that a concurrent `InitializeCheckpoint` created between the two. The unique index exists in the migrations of SQL Server, PostgreSQL and SQLite, and each provider wraps its unique violation in `DbUpdateException`. (2) `MessageStreamCheckpointHelper` re-reads the position with `GetStreamPosition` immediately before it saves a seed and skips the seed when one exists, resuming at that position plus one and recording `resumed` instead of `seeded`, which protects a hand-written store that does not follow the rule yet; it narrows the window and does not close it, so the store rule stays the contract. A failing re-read is a failed seed like a failing save.
- **Only `Last` and `Timestamp` are seeded.** `First` and `Offset(n)` do not change meaning between restarts and stay unpinned. `Timestamp` is pinned as a chunk-granular lower bound: a restart may redeliver messages from before the time, never skips one.
- **Transport capability.** `IStreamStartOffsetResolver` (`Flowly.Transport`, `Task<long?> ResolveStartOffset(queueName, partition, startPosition, ct)`) is a separate optional interface a client implements in addition to its stream capability; both stream background services detect it with a type test on the registered client and pass it to the helper. It is not a member of `IStreamCapableMessageBusClient`, and `CreatePartitionedStreamConsumer`'s signature is unchanged because the partitioned path resolves inside the existing per-partition `resolveStartPosition` delegate. `null` means "cannot be resolved without consuming" and leaves the lazy bootstrap in place (position stored after the first processed batch). Never answer too high: an offset that is too low redelivers, one that is too high loses data, so an approximate resolver rounds down.
- **Failure policy.** A resolver that throws or answers `null`, or a store that fails on the re-read or the seed save, is logged as a warning and counted (`outcome=seed_failed`); the handler still starts with the configured `StartPosition`. Cancellation propagates.
- **Telemetry lives in the helper.** `flowly.message.checkpoint.resolved` has the outcomes `resumed`, `fresh` (no seed attempted: no resolver, or `First`/`Offset`), `seeded` and `seed_failed`. Do not record these inside a checkpoint implementation.
- **No new clear-position tooling.** The CLI, Management API and PowerShell reset operations are unchanged; a seeded row lists like any other (position `-1` is shown as `-1`). Deleting the row makes the next start seed again.
- **InMemory** implements the resolver on `InMemoryStreamLog.ResolveStartOffset` (exact for every kind, per partition), but a checkpoint against an InMemory stream still throws, so it is a reference implementation.
- **`InitializeCheckpoint` is retried until it has completed once per reader.** The partitioned service records a partition as initialized only after `InitializeCheckpoint` has returned (`MessageStreamCheckpointHelper.ResolveStartPosition` reports it through its `checkpointInitialized` callback), so when it throws the next assignment of that partition calls it again, and once it has completed it is not called again for that partition for the process lifetime, however often the partition is revoked and reassigned. The bookkeeping is a set guarded by the service's lock, which stays correct when different partitions resolve concurrently; the transports serialize resolution only within one partition. A failure in `GetStreamPosition` or in the seed save after a successful `InitializeCheckpoint` does not cause initialization to run again. Seeding does not depend on `InitializeCheckpoint` (the built-in store's save upserts); a hand-written store whose save requires the row would fail the seed and fall back to the lazy bootstrap.

Any future offset-persistence work beyond this (e.g. cross-process coordination for non-partitioned streams) must be a deliberate, separately-designed feature — do not bolt it on as a side effect of an unrelated change. Partitioned streams have their own persistence story — see "Partitioned streams" below.

## Partitioned streams

A stream can be divided into `N` independent, ordered sub-logs via `[StreamPartitions(count)]` on the message contract (`src/Flowly/StreamPartitionsAttribute.cs`) — mirrors `[StreamRetention]`/`[QueueName]` living on the contract, not the handler. This is additive: a non-partitioned `MessageStreamHandler<T>`/`IMessageRecorder` is completely unaffected by this feature existing.

- **`IPartitionedStreamCapableMessageBusClient` is the delegation-model capability interface** (`src/Flowly/Transport/IPartitionedStreamCapableMessageBusClient.cs`; it extends `IStreamCapableMessageBusClient`, so a transport implementing it needs no separate stream declaration), checked eagerly at registration time like `IStreamCapableMessageBusClient`. Flowly does **not** implement its own cross-instance partition-assignment/rebalancing protocol — that's entirely the transport's job, using whatever native mechanism it has. Flowly's role is limited to running one independent `StreamPartitionRunner` per partition currently owned by this process, reacting to `IPartitionedStreamConsumer<TMessage>.PartitionAssigned`/`PartitionRevoked` as the transport reports them. Do not add partition-ownership coordination logic to core Flowly — it belongs in the transport adapter.
- **Batches never mix partitions.** Each owned partition gets its own `IMessageBusProcessor<TMessage>`, its own accumulate-batch loop, and its own halt-on-exhausted-retries — a poisoned partition holds only that partition (see "Halt, don't skip"); other partitions and the service itself keep running. `IMessageStreamContext<T>.Partition` tells the handler which partition a batch came from (`null` for non-partitioned streams).
- **`StreamPartitionRunner` is shared** between the non-partitioned (`MessageStreamProcessingBackgroundService`, one runner, `partition: null`) and partitioned (`PartitionedMessageStreamProcessingBackgroundService`, one runner per owned partition) background services — this is where the accumulate/retry/halt/checkpoint-save logic actually lives. Do not duplicate this logic when adding a new transport; extend `IMessageBusProcessor<TMessage>`/`IPartitionedStreamConsumer<TMessage>` instead.
- **Checkpointing composes unchanged.** `MessageStreamCheckpointHelper.ResolveStartPosition`/`SaveStreamPositionIfPresent` (shared by both background services) already key on `(ConsumerName, Partition)` — partitioned streams just supply a non-null `Partition`. For a newly-assigned partition, resolving the start position happens through the same `resolveStartPosition` delegate passed into `CreatePartitionedStreamConsumer`, called once per partition the first time this process becomes responsible for it.
- **Producer-side partition routing is a plain send-time concern, not a new sender abstraction.** `MessageProperties.PartitionKey` (set via `IMessageRecorder.Record(message, cancellationToken, partitionKey)` — deliberately placed *after* `cancellationToken`, not before, so existing positional `Record(message, ct)` call sites keep compiling) is resolved to a partition index by each transport's existing `IMessageBusSender` implementation, checking `StreamQueueManifest.GetPartitionCount(queueName)` at send time. No key routes round-robin; a key hashes consistently to the same partition every time. Do not introduce a separate "partitioned sender" interface — this reuses `IMessageBusSender.SendMessage` unchanged.

### InMemory partitioned streams — parity and local development, not scale

`InMemoryPartitionedStreamConsumer` assigns every partition immediately and permanently at `StartProcessingMessages` — `PartitionRevoked` is never raised, since InMemory is single-process by construction and there is no cross-instance ownership to hand off. Each partition is backed by its own `InMemoryStreamLog`, keyed internally as `{queueName}::{partition}` (see `InMemoryBroker.GetOrCreatePartitionedStreamLog`) — reuses the existing unpartitioned log implementation unchanged, just one instance per partition instead of one per queue. This exists so partition-aware handler code (routing, per-partition ordering, `[StreamPartitions]` wiring) can be developed and tested without a real broker — it gets none of the cross-instance throughput benefit partitioning exists for on RabbitMQ, because a single process can't offer that regardless of transport.

## Partition state model

Every partition a process owns has a state kept by the shared services, so every stream transport reports the same way: `Running` (a processing loop exists), `Waiting` (the start position could not be resolved, so no loop exists yet) and `Halted` (retries exhausted), plus the last error (message, type, time) and the time of the last state change, keyed by `(QueueName, ConsumerName, Partition)`; a non-partitioned stream is the single partition `null`. The model lives in `src/Flowly/MessageInfrastructure/StreamPartitions/` and is internal; `Flowly.ManagementApi` has `InternalsVisibleTo` to read it through `IStreamPartitionStateReader`.

- **Maintained by the shared services, never by transport code.** Transports keep reporting `PartitionAssigned`/`PartitionRevoked` and nothing else; do not add state reporting to a transport. `StreamPartitionStateReporter` (per handler registration) is the one writer: the services record `Running` when a loop starts (`StartPartitionLoop`, or the non-partitioned service once its start position is resolved), the non-partitioned service records `Waiting` (with the exception) for every failed attempt to resolve its start position (see "Non-partitioned start position retry" below), `StreamPartitionRunner` records `Halted` next to `IHandlerInstrumentation.RecordHalted`, the `resolveStartPosition` delegate of `PartitionedMessageStreamProcessingBackgroundService` records `Waiting` (with the exception) when resolution throws while no loop runs for that partition (a cancellation by shutdown is ignored), except for a consumer that retries the start position itself (`IStartPositionRetryingConsumer`, RabbitMQ), which raises `StartPositionResolutionExhausted` when its retry window ends and is recorded then, `PartitionRevoked` removes the entry (also for a halted or waiting partition, which has no runner; for a partition without a loop it removes only the `Waiting` entry the service recorded, matched by version, so a late revoke cannot delete the entry of a newer assignment), and `StopAsync` removes everything the registration owns.
- **A loop only updates the entry it started.** The runner holds a `StreamPartitionStateSession` carrying the entry's version, so a revoked or replaced loop cannot resurrect or overwrite the entry of its successor. Keep this when adding another place that writes a state.
- **Transitions only.** A state is written when the loop starts, halts, resumes, fails to resolve or is revoked, never per message or per batch; the registry is a plain lock around a dictionary and the processed-batch path never touches it. Repeating the current state only refreshes the error and does not count as a transition. The last error is kept when a partition returns to `Running`.
- **Observation, plus the halt/resume transitions.** The model records what happens: a waiting partition has no loop. The one transition the runner drives itself is `Halted` to `Running` when the held batch is resumed (`StreamPartitionStateSession.Resumed`); a revoked or replaced loop cannot write it.
- **Operator views.** `flowly.message.stream.partition.state` (observable gauge read from the registry by `HandlerInstrumentation`, `0` running / `1` waiting / `2` halted, one series per owned partition, gone after revocation) and `flowly.message.stream.partition.transitions` (counter, `state` tag is the state entered, recorded in `StreamPartitionStateReporter` through `IHandlerInstrumentation.RecordStreamPartitionTransition`), both tagged `handler`, `messaging.destination.name`, `consumer` and, for a partitioned stream only, `partition`. `builder.AddMessageStreamHealthCheck(name?, failureStatus?, tags?)` (core `Flowly`, transport independent, opt-in like the transport health checks) reports the registration's failure status, `Unhealthy` by default, while any owned partition is `Halted` or `Waiting`, and `Healthy` otherwise including when no partition is owned; the failing partitions are in the result data. A halted or waiting partition means consumption of it is not happening, which is why the default is `Unhealthy`; `failureStatus: HealthStatus.Degraded` keeps the instance in rotation.

## Non-partitioned start position retry

A non-partitioned stream has no transport that retries its start position, so `MessageStreamProcessingBackgroundService` does it itself. A failure while resolving the start position at boot (checkpoint `InitializeCheckpoint`, `GetStreamPosition`, or anything else `MessageStreamCheckpointHelper.ResolveStartPosition` throws) does not fault the service or stop the host: it is logged as a warning, recorded as `Waiting` for the partition `null` with the exception, and retried after a delay that starts at 1 second, doubles each time and is capped at 30 seconds, until it succeeds or the host stops. The delay is fixed and not configurable. On success the service creates the stream processor and the state becomes `Running` as before; shutdown during an attempt or the wait ends the service quietly and `StopAsync` removes the entry. Only start position resolution is covered: a failure creating the stream processor still faults the service. Because the state is `Waiting`, the state gauge, the transition counter and `AddMessageStreamHealthCheck` report the outage like they do for a waiting partition of a partitioned stream.

## Halt, don't skip, on exhausted retries

When in-process retries for a batch are exhausted, `StreamPartitionRunner` holds the failed batch: it does not advance past the offset, does not skip to the next message, and does not exit or drop anything. This is surfaced as a critical log entry plus `IHandlerInstrumentation.RecordHalted` telemetry (recorded after the partition state is `Halted`, so a signal for the halt always sees the state) and the `Halted` partition state. Do not "fix" a stuck stream by making the service skip past a poison batch — that silently loses data from an append-only log in a way that cannot be undone.

- **Hold, with backpressure.** A halted runner keeps the failed batch, its processor registered and itself alive, and reads nothing more from its buffer. The buffer is a bounded channel with capacity `MaxMessagesBeforeProcessing` (at least 1), written with `WriteAsync`, so the `ProcessMessage` delegate the transport awaits stops completing once one further batch is buffered. A transport therefore only has to await that delegate before delivering the next message of a queue or partition (see `IMessageBusProcessor<TMessage>.ProcessMessage`); the broker keeps the rest of the stream, nothing is dropped, and no "not currently processing" warning is logged for a held partition. Memory while halted is bounded by the held batch plus one buffered batch plus whatever the transport itself has already read. Do not make the buffer unbounded again and do not stop the processor to halt: a stopped or unregistered processor makes the transport drop what it still delivers.
- **Resume is an operator action only.** `IStreamPartitionResumer.Resume(StreamPartitionKey)` (internal; `Flowly.ManagementApi` has `InternalsVisibleTo`) addresses a live runner by queue, consumer name and partition (`null` for a non-partitioned stream) and returns `Resumed`, `NotHalted` or `NotOwned`. It is backed by `StreamPartitionResumeRegistry`, registered in DI next to the state registry by `StreamPartitionStateRegistry.GetOrCreate`; each runner registers itself for the lifetime of `Run`. Nothing in Flowly resumes automatically. The operator interface is the Management API and the PowerShell cmdlets, see "Operator control of partitions" below.
- **What a resume does.** It moves the state `Halted` to `Running`, re-runs the held batch in place with a fresh set of in-process retries (the same semantics as a new batch), and when that succeeds completes and checkpoints the batch and continues contiguously with the buffered messages (a batch held because its completion or checkpoint save failed skips the handler, see below). When the batch fails again it halts again (state back to `Halted`, `RecordHalted` counted again) and can be resumed again. The batch is counted as received once, not once per resume. No checkpoint is saved for a held batch before it succeeds.
- **Revoke and stop.** A revoked or stopped partition cancels its held runner (the services cancel the runner before stopping or disposing its processor, which also releases a transport delivery that is blocked on the buffer), removes the state entry and the resume handle, and a new owner replays from the stored position, including the poison batch. A halted partition is not pinned to its instance (observed live on RabbitMQ and on the Event Hubs emulator). The automatic recreation of the RabbitMQ consumer for a partition with an unresolved start position revokes every loop and so also releases the hold of a halted partition, which replays and halts again (see `message-streaming-rabbitmq.md`).
- **A failed acknowledgement or checkpoint save is not a handler failure.** After the handler returned, `StreamPartitionRunner` completes the batch's messages and saves the checkpoint in separate steps, each with its own in-process retry loop using the same `[RetryPolicy]` count and delay. The handler is never run again for a batch it already handled: a failing `Complete` or `SaveStreamPosition` retries only that step (a retry of the completion skips the messages already completed). When the step still fails after the retries the partition halts as for a handler failure (same state, hold with backpressure, `RecordHalted`), but the last error is a `StreamBatchAcknowledgementException` whose message says the handler succeeded and that completion or the checkpoint save failed, with the original exception as inner exception, so an operator can tell it apart from a handler failure. A resume then re-runs only the remaining completion and the save of the held batch; the handler runs again for it only after a revoke, a stop or a restart, which replay it from the stored position. Without `[RetryPolicy]` a single failing save halts the partition. A checkpoint store outage therefore halts every partition that saves during it, and a resume after the store is back continues without handling any batch twice.
- **Non-partitioned streams** halt the same way with their single runner, and the same resume hook (`partition: null`).

## Operator control of partitions (Management API and PowerShell)

`Flowly.ManagementApi` exposes the partition state and the resume hook as `GET {BasePath}/message-streams/partitions` (Read, optional `queue`, `consumer`, `partition`, `state` filters) and `POST {BasePath}/message-streams/partitions/resume` (Write, body `{ queueName, consumerName, partition }`), mirrored by `Get-FlowlyMessageStreamPartition` and `Resume-FlowlyMessageStreamPartition` (`src/Flowly.ManagementApi/MessageStreams/`, `src/Flowly.PowerShell/Cmdlets/`). Decided design, not to be re-derived differently:

- **A runtime control on the live consumer, per instance.** The actions read `IStreamPartitionStateReader` and call `IStreamPartitionResumer`, both of the process that answers, so they work only in a process that hosts the handlers and only for the partitions that process owns. There is no cross-instance signalling and no deliberate hand-over; with several instances the operator addresses the owner, and a partition that moved answers `404` on the old owner.
- **Feature detection.** `UseFlowlyManagementApi()` maps both actions when `IStreamPartitionStateReader` and `IStreamPartitionResumer` are in DI. `AddFlowly` always registers them (`StreamPartitionStateRegistry.GetOrCreate`), so the actions exist in every Flowly host and list nothing when no stream handler is registered. They are authorized like every other action (Read for the list, Write for the resume).
- **Addressing.** A partition is addressed by `(queueName, consumerName, partition)`, `partition` omitted or `null` for a non-partitioned stream, the same key as the state registry and the checkpoint identity.
- **Resume outcomes.** `204` resumed; `404` the state registry has no entry for the key (not owned, also after a revoke); `409` the entry exists and is `Running` or `Waiting` (the resume result `NotHalted` from the resumer after the state read says `Halted` is also `409`, `NotOwned` is `404`); `400` blank queue or consumer, or an unknown `state` filter. Errors are problem details whose `detail` the cmdlet surfaces. A resume never skips the held batch.
- **Observed live** (`docs/ai/message-streaming-verification.md`, "Management API and PowerShell partition control"): with two and three RabbitMQ instances each instance listed and resumed only its own partitions, a resume addressed to a non-owner answered `404`, a halted partition that moved (instance joined or stopped) was replayed and halted again on the new owner while the old owner answered `404`, and nothing was skipped or handled twice; a halted partition on the Event Hubs emulator with the blob ownership container, a partition on InMemory and a non-partitioned stream (`partition` omitted or `null`) resumed in place the same way. Authorization with a Read-only, a Write-only and a both-roles OAuth2 token behaved as documented for the `roles` claim; a token that carries the requirement only in the scope claim (`scp`, which the JWT bearer handler maps to `http://schemas.microsoft.com/identity/claims/scope`) is authorized, because the requirement handler matches both claim types (see the verification record).
- **No retry-now for a waiting partition.** A `Waiting` partition has no loop and is retried by its transport (RabbitMQ: the bounded listener window and the consumer recreation with growing delay; Event Hubs: the SDK's load balancing cycle) or, for a non-partitioned stream, by the service itself (see "Non-partitioned start position retry"), so the resume answers `409` for it and no action shortens the wait.

## In-process retry, not requeue

Stream retries are a plain in-memory loop over the already-received batch, NOT a re-publish to the queue (unlike `MessageProcessingBackgroundService.RepublishForRetry` / `BatchProcessingBackgroundService.RepublishBatchForRetry`). Requeuing into an immutable, replayable stream would permanently corrupt it with retry noise for every future consumer reading from `StartPosition.First()`. Not advancing the offset is itself the retry mechanism — do not add a republish path to `MessageStreamProcessingBackgroundService`.

## Ask, don't assume

Any future ambiguity in this feature area (new retention knobs, offset persistence, cross-transport support, dead-letter recovery for halted streams, consumer-group semantics, etc.) must be resolved by asking rather than assuming — mirroring the design process that produced this feature. Do not guess at a shape for a new stream-related API surface and ship it; confirm with the user first.

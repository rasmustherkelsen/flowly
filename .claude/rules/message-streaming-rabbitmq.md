# RabbitMQ Message Streaming Conventions

RabbitMQ-specific stream rules; the transport-independent rules are in `message-streaming-conventions.md`. Evidence: `docs/ai/message-streaming-verification.md`.

## First-run offset probe

- **RabbitMQ resolves with an AMQP probe consumer** (`RabbitMqStreamOffsetProbe`, behind the internal `IStreamOffsetProbe`; no Stream protocol port). It attaches a consumer on a dedicated short-lived channel of the shared consumer connection at the last chunk (`x-stream-offset = last`) for `Last`, or at the AMQP timestamp for `Timestamp` (on a partitioned stream, the `{queue}-{partition}` stream), acknowledges in batches (`multiple = true`, every 250 deliveries, prefetch 1000), and reads `x-stream-offset` from each delivery. `Last` is the highest delivered offset plus one; `Timestamp` is the first delivered offset. Collection ends after a 250 ms quiet window or at most 1 s after the first delivery, whichever comes first (on a stream that keeps receiving messages the answer is therefore a tail from at most that long ago: lower, never higher). Nothing delivered within 1 s of the consumer attaching means "empty" only when the broker's passive queue declare also reports `0` messages (that count lags: it reported `0` for streams holding thousands of messages shortly after publishing, so it is used only to rule empty out, never as the tail); a non-zero count with nothing delivered is inconclusive (`null`). A `Timestamp` that nothing matches is confirmed with a second probe at the last chunk and answers `0` only when that is empty too, otherwise `null`. The consumer is always cancelled and the channel closed. The acknowledgement path takes a gate that is closed before the channel is: an acknowledgement sent on a channel that is being closed is a protocol error that makes the broker close the whole shared connection (seen against the live broker while probing a stream that kept receiving messages).

## RabbitMQ Super Streams

- **Topology (the exchange + per-partition streams + bindings) is declared over plain AMQP** — `RabbitMqMessagingTopologyCreator.DeclarePartitionedStreamTopology` creates a direct exchange named after the queue, one stream queue per partition named `{queueName}-{partition}` (declared via the same `DeclareStreamQueue` a non-partitioned stream uses), and binds each partition stream to the exchange with the partition index as the routing key. This matches how a Super Stream can be created with any AMQP 0.9.1 client, not just the RabbitMQ Stream protocol client — no new dependency needed just to provision the topology.
- **Producing uses the same plain-AMQP path** — `RabbitMqMessageBusSender` publishes to the partitioned queue's exchange with the resolved partition index as the routing key instead of publishing directly to a queue via the default exchange. No Stream protocol client involvement on the producer side at all.
- **Consuming needs the RabbitMQ Stream protocol client** (`RabbitMQ.Stream.Client` NuGet package, `RabbitMqPartitionedStreamConsumer`) — this is the one piece that genuinely can't be done over AMQP: broker-coordinated Single Active Consumer rebalancing. The client's `ConsumerConfig` (`RabbitMQ.Stream.Client.Reliable` namespace, not the bare `RabbitMQ.Stream.Client` namespace) is configured with `IsSuperStream = true, IsSingleActiveConsumer = true`; its `ConsumerUpdateListener` callback (`(reference, stream, isActive) => Task<IOffsetType>`) is both the ownership-change signal (`isActive` toggling maps to `PartitionAssigned`/`PartitionRevoked`) and where the resume offset for a newly-active partition is resolved — this is also where a registered `MessageStreamCheckpoint<TMessage>` gets consulted, per partition, threading Flowly's own checkpoint straight into the broker's native rebalancing protocol rather than needing the client's own (Blob-Storage-style, for other clients) checkpoint mechanism.
- **The Stream protocol uses a separate port from AMQP** (5552 by default, vs. AMQP's 5672) on the same host — `RabbitMqConnectionPool.GetStreamSystem` derives a `StreamSystemConfig` from the same connection URI already used for AMQP, resolving the endpoint via `RabbitMqConnectionPool.ResolveStreamEndpoint` (host from the URI, port from the `streamPort` constructor parameter). The port is configurable via `UseRabbitMq(..., streamPort: <port>)` — a plain trailing optional `int streamPort = 5552` parameter on `UseRabbitMq`, threaded through `RegisterRabbitMq` into `new RabbitMqConnectionPool(uri, streamPort)`; this deliberately matches the existing flat-optional-parameter convention rather than introducing a `RabbitMqOptions` aggregate. Host scope stays fixed to the AMQP connection's host — no independent stream-host override, since RabbitMQ's stream protocol is always a second port on the same broker host. Any deployment target must publish whichever port is configured on the same host as the AMQP connection — both `flowlyapp`'s `docker-compose.yml` (`5552:5552`, conditioned on `UseRabbitMqStreamPartitions`) and the `flowlyaspireapp` AppHost (`.WithEndpoint(name: "stream", port: 5552, targetPort: 5552)`, conditioned on the same symbol) still default to the standard port 5552 — the templates do not expose a CLI flag for this; a user who changes their deployment's published stream port passes the matching `streamPort:` value to `UseRabbitMq` directly.
- **Partition index is recovered from the source stream name by convention**, not queried from the broker — `RabbitMqPartitionedStreamConsumer` parses `{queueName}-{partition}` directly out of the `sourceStream` argument the client's `MessageHandler` callback provides, rather than calling `StreamSystem.QueryPartition` to cross-check per-message. `QueryPartition` is used elsewhere, at startup — see the next bullet.
- **Declared partition count is validated against the broker at startup, in both `createTopology` modes; drift fails startup.** A partition stream count on the broker that differs from the contract's `[StreamPartitions(n)]` throws `InvalidOperationException` naming the stream, the declared count and the broker's count. Left unchecked, a mismatch lets `RabbitMqMessageBusSender.ResolvePartition` compute routing keys with no matching exchange binding — publishes silently dropped, no broker error — or leaves real broker partitions permanently unconsumed, since the consumer only reacts to whatever the broker reports and never cross-checks the declared count itself. One comparison and one message live in `RabbitMqPartitionedStreamCountVerifier`, which calls `IRabbitMqConnectionPool.QueryStreamPartitions` (a thin wrapper over `StreamSystem.QueryPartition`, so it needs the Stream protocol port) and is used from two places, both local to `Flowly.RabbitMQ`:
  - **`createTopology: false`:** `RabbitMqPartitionedStreamTopologyValidator` — a dedicated `IMessagingTopologyValidator` registered alongside `RabbitMqRetryTopologyValidator`, not folded into it — runs the verifier for every queue `StreamQueueManifest.GetPartitionCount` reports as partitioned and turns a missing Super Stream into an `InvalidOperationException` about pre-provisioning. This deliberately mirrors the existing retry-queue validation instead of introducing a new invocation point: `QueueRegistrarHostedService` runs *every* `IMessagingTopologyValidator` matching a provider (not just the first), so a second validator composes for free.
  - **`createTopology: true`:** `RabbitMqMessagingTopologyCreator.DeclareQueueTopology` runs the same verifier immediately after the additive `DeclarePartitionedStreamTopology`. Core `QueueRegistrarHostedService` runs validators only when topology creation is off, and the topology creator interface is deliberately not changed for this, so the check sits in the RabbitMQ creator. Missing partition streams and bindings are created first, so fewer partitions on the broker than declared are topped up and pass, while more partitions than declared (for example after lowering `[StreamPartitions(n)]`) fail.
  - **No reconciliation, no live partition-count change.** Flowly never deletes or re-creates partition streams or bindings to make the broker match the contract; resolving drift is an operator action on the broker. Changing the partition count of a live stream is not supported: re-partitioning changes which partition a key maps to, so it is treated as drift and fails startup, and this limitation is stated in the user-facing documentation. The check needs the Stream protocol port at startup, so a sender-only host with `createTopology: true` and a partitioned contract now also needs `streamPort` to be reachable (previously only a consuming host did).
- **Start position resolution failure.** When `resolveStartPosition` throws inside `ConsumerUpdateListener`, the Stream client swallows it and attaches the partition at its default offset `next`, ignoring the configured or stored position. `RabbitMqPartitionedStreamConsumer.OnConsumerUpdate` therefore resolves the start position first, before registering the partition's processor and raising `PartitionAssigned`, and logs and rethrows a failure: no loop exists for the partition and nothing is checkpointed (see "Recovery of an unresolved start position"). Resolving after the loop had started would silently ignore a stored position and move the checkpoint past the unprocessed backlog.
- **No revoke after a lost connection.** After a broker restart the client reports `isActive: true` again without a preceding `isActive: false`, so `OnConsumerUpdate` revokes a live loop for that partition and waits for every earlier revocation of it before starting a new one. The offset returned for `isActive: false` is ignored; the consumer returns `OffsetTypeFirst`.
- **Rebalance and crash duplicates are bounded.** A new owner (rebalance or `kill -9`) replays the in-flight batch from the stored position, so duplicates are bounded by one batch per affected partition; handlers must be idempotent.
- **Super Streams created outside Flowly** (for example with `rabbitmq-streams add_super_stream`) are consumed and published to unchanged with `createTopology: false`. With `createTopology: true` the AMQP declaration fails (`PRECONDITION_FAILED - inequivalent arg 'x-queue-leader-locator'`) before any count check, because Flowly's declaration is deliberately not made compatible with them.
- **Stream port.** A wrong `streamPort` fails startup with `StreamSystemInitialisationException`. The configured endpoint is used for the initial connection and stream metadata; the consuming connection goes to the `stream.advertised_host`/`stream.advertised_port` the broker reports for the partition's leader (the configured endpoint is kept when the host is loopback), so a non-loopback broker must advertise an address the client can reach. Flowly passes a single endpoint and no address resolver, so a load balancer in front of the stream port is not supported.

## Recovery of an unresolved start position

A partition whose start position cannot be resolved (typically the checkpoint store is down while the partition is assigned) recovers without a process restart. The recovery lives entirely in `RabbitMqPartitionedStreamConsumer` behind the unchanged `IPartitionedStreamConsumer<TMessage>` contract; the shared services only observe it through `PartitionRevoked`/`PartitionAssigned` and the `resolveStartPosition` delegate. Decided, not to be re-derived:

- **The reliable `Consumer` stays.** No reflection into it and no switch to the raw super stream consumer: a single partition is never re-attached on its own, the whole consumer is recreated instead.
- **Bounded retry inside `ConsumerUpdateListener`.** `RabbitMqPartitionedStreamConsumer.OnConsumerUpdate` retries `resolveStartPosition` with a doubling delay (0.5 s, ceiling 5 s) until a 40 second window has passed, measured from the start of the callback so that a wait for an earlier revocation of the same partition counts. The window is kept well under the 60 seconds after which the broker closes a connection whose listener callback has not returned. The constants are internal (`RabbitMqPartitionedStreamTimings`), not options. The attempt runs with a token that is cancelled at the window end and by the generation, so a resolver that honors cancellation does not outlive the window (an attempt that is still pending can no longer complete later and write a stale bootstrap seed), and `Task.WaitAsync` bounds it at the window end, so a resolver that ignores cancellation is abandoned at the end of the window (it keeps running in the background); cancellation by shutdown or recreation ends the callback with `OperationCanceledException` and records nothing. A failed attempt that a later one absorbs does not make the partition `Waiting`: the consumer implements the internal `IStartPositionRetryingConsumer` (core, `Flowly.MessageInfrastructure.StreamPartitions`), so `PartitionedMessageStreamProcessingBackgroundService` does not record `Waiting` from a failed `resolveStartPosition` call and instead records it when the consumer raises `StartPositionResolutionExhausted` at the end of the window (the final failure, never for a cancellation by shutdown or recreation). A short outage therefore shows no `Waiting` entry and no transition, only `Running` when the loop starts. A consumer without that interface, such as Event Hubs or InMemory, has no retry window and keeps recording `Waiting` from every failed call.
- **While the callback waits, that partition's connection delivers nothing** (one consumer per connection, the client default Flowly keeps), so nothing is dropped and other partitions are unaffected. The same wait holds the partition for the other instances of the consumer group: the broker does not activate another consumer for the partition until the callback has returned.
- **At the end of the window the fallback is unchanged and data safe.** The last failure is logged and rethrown, the client swallows it and attaches the partition at `next`, no processor or loop exists and nothing is checkpointed. What the client then delivers for the partition is dropped by `RabbitMqStreamPartitionDropSummary`: every drop increments `flowly.message.stream.partition.dropped` (tags `messaging.destination.name`, `consumer`, `partition`; the counter is created by the transport on the `Flowly` meter because transports have no `IHandlerInstrumentation`), and the log gets a summary per partition (the first drop right away, then at most one every 30 seconds, with the number dropped since the previous summary and the last start position error; the leftover count is logged when the partition starts). There is no per-message warning. Nothing is skipped: the dropped messages are delivered again from the stored position once the partition starts (halt-don't-skip holds).
- **Automatic recreation of the whole consumer.** A partition that fails marks itself in the current consumer generation and triggers `RabbitMqWaitingPartitionRecovery`: one loop per consumer, so recreations never overlap. After a delay that starts at 5 seconds, doubles and is capped at 2 minutes, it cancels the generation (aborting the callbacks that wait), closes the Stream consumer, awaits the callbacks that are still running, stops every live processing loop (`PartitionRevoked` for each, awaited) and creates the consumer again; the broker then offers every partition to this process once more and the listener resolves them anew, the healthy ones from their checkpoints. The consumer is closed before the loops are stopped, so nothing is delivered while they stop and no drop is counted for the recreation. After a recreation the recovery waits a 2 second settle time for the broker to report the partitions again, then ends when no partition is waiting, or goes on with the next, longer delay; the need is checked again after each delay, so a partition that resolved or moved away during the delay ends it. A failing `Consumer.Create` is logged and tried again after the next delay. The recovery ends when the consumer is stopped, which also cancels a recreation in progress.
- **Stand-down after repeated failed recreations.** Without a hand-over a partition that one instance cannot resolve starves when another instance could run it (for example only the first one has a broken connection to the checkpoint store): the owner holds it for the whole bounded wait and the broker activates it on the same instance again after each recreation, so the other instance runs it only between two recreations of the first (live: 125 of 2970 messages in six minutes, see the verification record). Decided: after 3 consecutive failed recreations the instance keeps its consumer closed for a cool-down so the broker moves the partitions to another instance, then recreates it. The constants are internal (`RabbitMqPartitionedStreamTimings.StandDownAfterFailedRecreations`, `StandDownInitial`, `StandDownMax`), not options. Exact definitions, not to be re-derived:
  - **A failed recreation** is a recreation that created the consumer and after which, once the settle time has passed and the callbacks still running (each bounded by the 40 second window) have returned, a partition is still waiting. A recreation whose `Consumer.Create` failed is neither counted nor does it reset the count (a broker outage must not turn into a stand-down). The count is per consumer, not per partition: the recovery is one loop per consumer and a recreation acts on the whole consumer.
  - **The stand-down** closes the consumer exactly as a recreation does (live loops stopped and revoked, callbacks awaited, consumer closed), so every partition of this instance is revoked, the healthy ones too (accepted cost: they move to another instance, and a lone instance consumes nothing for the cool-down), and keeps it closed for the cool-down. The recreation that follows the cool-down is unconditional, because a closed consumer would otherwise stay closed: the cool-down only delays, it never stops the only instance from recovering. After it the usual settle time and judgement apply.
  - **The cool-down** is 1 minute, doubling with each successive stand-down (1, 2, 4 minutes) up to a 5 minute ceiling (5, 5, ...). The failed count restarts at zero after each stand-down; the recreation back-off (5 s doubling to 2 min) keeps running across it. When no partition is waiting any more (every partition resolved, moved to another instance, or was revoked by the broker) the recovery ends and the failed count, the back-off and the cool-down escalation all reset.
  - **Shutdown or stop during a cool-down** cancels it at once and no recreation follows; the consumer stays closed and the stop completes promptly. A broker revocation cannot arrive during a cool-down (the consumer is closed); a waiting partition that moved to another instance before the stand-down ends the recovery as before.
  - **Visibility.** One warning per stand-down ("Standing down the partitioned consumer of stream queue ...": cool-down length, stand-down number, number of failed recreations) and the counter `flowly.message.stream.partition.stand_downs` (tags `messaging.destination.name` and `consumer`, no `partition` tag because the whole consumer stands down; created by the recovery on the `Flowly` meter like the drop counter). The `Waiting` partition state model is unchanged: a waiting partition keeps its entry through the cool-down (so the health check of a lone instance stays unhealthy) and is released after the settle time of the next recreation when it did not come back.
  - **Observed effect (two instances, live).** The instance that cannot resolve gets partitions back when its consumer is created again after the cool-down: the broker spreads the partitions of a super stream over the consumers of the group when one joins, and the failing partition returned to the standing-down instance while the other partitions stayed where they were. The stand-down therefore relieves the starvation for the length of the cool-down (the other instance drains the whole backlog of the partition meanwhile) and does not end it: with one failing instance and one healthy one the partition progressed 54 percent of the published messages in 8 minutes against 14 percent without the stand-down. Figures and scenarios: `docs/ai/message-streaming-verification.md`.
  - **Halted partitions** are not counted and not touched: only a waiting partition starts or prolongs the recovery. A stand-down revokes every live loop like a recreation, so it releases the hold of a halted partition the same way (see "Interplay with a halted partition"), with a longer gap before the partition is assigned again.
- **Generations disarm the previous incarnation.** Every consumer incarnation is a `Generation` with its own token. Once cancelled (recreation, stop, dispose), its message and listener callbacks do nothing: a late callback cannot register a processor, start a loop or count as a drop. The reliable client's own reconnect handling stops with `Close()` (it reports `ClosedByUser`), so there is no reconnect handler of Flowly's to disarm. Revocation and assignment sequencing is unchanged: the live loop of a partition is revoked before a new one starts, and the recreation also waits for pending revocations.
- **No stale state.** A waiting partition keeps its `Waiting` entry (and its `StateChangedAt`) across recreations; the healthy partitions are removed by their revocation and recorded `Running` again when reassigned. A waiting partition that does not come back in the new incarnation (the broker gave it to another instance) is released with `PartitionRevoked` after the settle time, and a waiting partition revoked by the broker (`isActive: false`) ends the recovery, which clears its entry.
- **Accepted cost.** Each recreation redelivers the in-flight batch of every healthy partition (the handler has to be idempotent, as for every restart or rebalance), and the broker may hand partitions over between the instances of the group. The owning instance retries itself with growing delays; the only deliberate hand-over is the stand-down after 3 failed recreations (see above). Replay always starts from the stored position.
- **Interplay with a halted partition.** A recreation revokes every live loop, and revoking cancels a held runner of a halted partition (see "Halt, don't skip" in message-streaming-conventions.md), so a partition halted by its handler loses its hold when a different partition's start position triggers a recreation: its state entry and resume handle are removed, the re-assigned partition replays from the stored position, runs the poison batch again and halts again after its retries (state `Halted`, removed, `Running`, `Halted`). Nothing is skipped and nothing is stored for the held batch; an operator resume hook obtained before the recreation answers `NotOwned` afterwards. This is the documented consequence, not a defect, and a stand-down has the same effect (a longer gap before the partition is assigned again, to this or another instance). The order inside a recreation matters for it: the loops are stopped before the Stream consumer is closed, because a halted partition holds its delivery back (backpressure) and only stopping its held runner releases that delivery, so closing the consumer first could wait for a delivery that only the stopped loop can release.

Any future ambiguity in this sub-area (consumer-group semantics beyond Single Active Consumer, cross-broker partition rebalancing tuning, etc.) still falls under "Ask, don't assume" below. Reconciling broker drift and live partition-count changes are decided as not supported (see above), not open questions.
